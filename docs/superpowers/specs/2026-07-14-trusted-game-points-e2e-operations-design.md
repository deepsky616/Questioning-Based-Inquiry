# 질문놀이 신뢰 기록, 관통 시험, 운영 기록 설계

## 목표

질문놀이 화면의 점수 안내를 실제 서버 정책과 맞추고, 모든 놀이 모드의 점수 근거를 서버가 직접 검증해 기록한다. 이어서 교사와 학생의 핵심 수업 흐름을 한 번에 확인하는 화면 시험과 민감 자료를 남기지 않는 보안 사건 기록을 추가한다.

완료 조건은 다음과 같다.

- 지원하지 않는 점수 요청과 가짜 점수 결과가 화면에 나타나지 않는다.
- 친구, 혼자, 도움 모드의 점수는 완료된 서버 실행 기록에서만 계산된다.
- 같은 동작 재전송과 동시 요청이 활동이나 점수를 두 번 만들지 않는다.
- 기존 계정, 질문, 수업, 점수 기록은 옮기거나 다시 계산하지 않는다.
- 교사 배포부터 학생 질문, 교사 확인과 점수 승인, 알림까지 한 화면 시험으로 이어진다.
- 가입 코드 실패, 범위 밖 접근, 방 권한 거절, 점수 증거 거절이 민감 자료 없이 구조화 기록으로 남는다.

## 범위 분해와 진행 순서

작업은 아래 네 단계로 나누며 앞 단계의 정책을 다음 단계가 재사용한다.

1. 점수 화면과 서버 가능 여부 일치
2. 서버 권위 실행 및 활동 기록
3. 교사와 학생 핵심 흐름 화면 시험
4. 보안 사건 기록과 외부 경보 연결점

구현은 공통 기반과 이어 말하기를 첫 세로 단위로 완성한 뒤 질문 주사위, 까바놀이, 질문 사다리, 이야기 주사위, 짝 찾기, 미스터리 상자 순서로 넓힌다. 각 단위는 자료 구조, 서버 명령, 친구·혼자·도움 모드 화면, 단위 시험과 화면 시험을 함께 끝낸다. 해당 단위의 모든 시험이 통과한 뒤에만 가능 여부를 `verified`로 바꾸며, 아직 준비되지 않은 놀이는 자동으로 비활성 상태를 유지한다.

## 검토한 접근

### 접근 1: 화면만 정리하고 기존 점수 차단 유지

가장 빠르고 자료 변경이 없다. 하지만 점수 기능을 다시 사용할 수 없고 사용자의 목표를 절반만 해결한다.

### 접근 2: 방 상태 안에 검증 활동을 함께 저장

친구 모드는 기존 `game_rooms.data` 안에 검증 기록을 넣고, 혼자 및 도움 모드만 새 실행 표를 사용한다. 변경량은 비교적 작지만 활동 검색, 운영 조사, 만료 처리, 동시 갱신이 큰 JSON 한 행에 집중된다.

### 접근 3: 실행과 활동을 추가 전용 자료로 분리

새 `GameRun`과 `GameActivity`를 모든 모드의 공통 점수 근거로 사용한다. 화면 상태와 점수 근거가 분리되고, 요청 식별값과 순번 고유 제약으로 재전송과 동시 쓰기를 데이터베이스에서도 막을 수 있다.

**선택:** 접근 3을 사용한다. 기존 자료를 수정하지 않는 추가 마이그레이션이며, 가장 명확한 권한 경계와 점수 감사 근거를 제공한다.

## 1단계: 점수 화면 정책

### 공통 가능 여부

`src/lib/game-point-capabilities.ts`에 놀이와 모드별 상태를 정의한다.

- `disabled`: 서버 증거가 없어 점수를 요청하지 않음
- `verified`: 서버 실행 기록으로 점수를 지급할 수 있음
- `reason`: 사용자 안내에 쓰는 안정된 사유 코드

화면과 점수 경로가 같은 정책을 가져다 쓴다. 서버가 지원하지 않는 모드는 화면에서 요청 자체를 보내지 않는다.

### 친구 모드 결과

`RoomResult`는 다음 원칙을 따른다.

- `gameState.awardResult`처럼 참가자가 쓸 수 있는 값을 점수 결과로 표시하지 않는다.
- 서버의 실행 결과 조회 응답만 포인트 결과로 표시한다.
- 비활성 놀이에는 활동 점수만 보여 주고 포인트가 저장되지 않는다는 짧은 안내를 표시한다.
- 재시도해도 성공할 수 없는 오류에는 재시도 단추를 보여 주지 않는다.

### 혼자 및 도움 모드

`useSingleAward`는 비활성 정책이면 요청을 보내지 않고 준비 상태를 반환한다. 모든 일곱 놀이 결과 화면은 같은 `AwardBadge`를 사용해 지급, 일일 상한, 준비 상태를 일관되게 표시한다.

### 포인트 안내

학생 포인트 화면의 설명은 실제 활성 정책에서 만들어진다. 모든 놀이가 점수를 준다는 고정 문구와 혼자 및 도움 모드가 항상 낮은 점수를 준다는 문구를 제거한다.

## 2단계: 서버 권위 실행과 활동

### 자료 구조

새 `GameRun`은 한 번의 놀이 실행을 나타낸다.

- `id`: 서버 실행 식별값
- `gameId`: 놀이 종류
- `mode`: `ROOM`, `SOLO`, `AI`
- `ownerId`: 실행을 시작한 사용자를 가리키는 선택 외래 키
- `creationRequestId`, `creationRequestFingerprint`: 실행 생성 재전송을 구분하는 값
- `roomLifetimeKey`: 친구 방의 코드와 생성 시각을 합친 선택 고유값
- `participants`: 서버가 잠근 방 자료에서 만든 시작 시점 참가자 식별값, 역할, 점수 자격
- `status`: `ACTIVE`, `COMPLETED`, `PENDING_APPROVAL`, `SETTLED`, `EXPIRED`
- `state`: 서버만 해석하고 갱신하는 놀이별 상태
- `version`: 낙관적 동시 처리 버전
- `scoreDate`: 완료 순간 서버가 서울 날짜로 고정한 일일 상한 기준일
- `completedAt`, `settledAt`, `expiresAt`, 생성 및 수정 시각

새 `GameActivity`는 점수 근거가 되는 검증 동작을 추가 전용으로 저장한다.

- `runId`, `actorId`: 실행과 행위 사용자를 가리키는 외래 키이며 행위 사용자는 삭제 뒤 비울 수 있음
- `requestId`: 화면이 동작마다 만든 재전송 식별값
- `requestFingerprint`: 명령 종류와 정규화한 입력으로 만든 해시
- `sequence`: 실행 안 순번
- `type`: 놀이별 안정된 활동 종류
- `payload`: 명령 종류, 글자 수, 키 기반 내용 해시처럼 검증에 필요한 최소 내용
- `validQuestionCount`, `scoreValue`
- `responseSnapshot`: 같은 요청 재전송 때 돌려줄 민감값 없는 응답
- 생성 시각

`payload` 내용 해시는 배포 환경에서 필수인 전용 `GAME_ACTIVITY_HASH_SECRET`으로 만든다. `responseSnapshot`에는 사용자 작성 원문을 넣지 않고 요청 확인값, 버전, 서버가 공개한 주사위·카드 결과, 점수 요약만 저장한다.

고유 제약은 `GameRun(ownerId, creationRequestId)`, `GameRun(roomLifetimeKey)`, `GameActivity(runId, requestId)`, `GameActivity(runId, sequence)`에 둔다. `PointLog`에는 `GameRun`을 직접 가리키는 선택 `gameRunId`를 추가하고 기존 행은 모두 `null`로 유지한다. `(studentId, gameRunId, bonusType)` 고유 제약을 새 중복 지급 기준으로 사용한다. 기존 `roomCode` 고유 제약에도 `run:<runId>`를 기록해 이전 경로와의 중복을 한 번 더 막는다.

외래 키 삭제 규칙은 다음과 같다.

- `GameRun.ownerId`와 `GameActivity.actorId`는 선택값과 `SetNull`로 두어 교사나 참가자 계정 삭제가 다른 학생의 지급 근거를 지우지 않게 한다.
- `GameActivity.runId`는 실행 삭제에 연동해 삭제한다.
- `PointLog.gameRunId`는 `Restrict`로 두어 점수 기록이 연결된 실행이 실수로 지워지지 않게 한다.
- 학생 계정 삭제 때 해당 학생의 `PointLog`만 기존 연동 규칙으로 삭제하고 다른 학생의 실행과 점수 기록은 유지한다. 교사 계정 삭제 때 실행 소유자만 비운다.

### 권한, 공개 범위, 자료 수명

- 친구 모드 실행 생성과 완료 요청은 잠근 방의 현재 방장만 할 수 있다. 방장이 학생이면 완료는 교사 확인 대기 기록까지만 만들고 학생 합계는 바꾸지 않는다.
- 참가자 목록은 요청 본문을 받지 않고 잠근 방 자료에서만 만든다. 실행 시작 참가자와 동작 시점 방 참가자의 교집합에 속한 인증 사용자만 자신의 동작을 보낼 수 있다. 실행 시작 뒤 들어온 사용자는 현재 방 참가자여도 해당 실행에 참여할 수 없으며 인공지능 동작은 서버만 만든다.
- 학생 방에서는 방장과 학교, 학년, 반이 같은 실제 `STUDENT` 참가자만 확인 대기 점수 대상이다. 다른 학생의 동작이나 점수를 대신 만들 수 없으며 담당 교사가 기존 점수 확인 화면에서 승인해야 합계에 반영된다.
- 교사 방에서는 현재 교사의 학교와 담당 학급 범위에 속한 참가 학생만 점수 대상이며, 교사 자신과 범위 밖 학생은 제외한다. 교사 방 완료는 검증된 점수를 바로 승인할 수 있다.
- 역할, 학교, 학년, 반, 담당 학급 자격은 생성 때뿐 아니라 모든 동작과 완료 거래 안에서 다시 읽는다. 중간에 자격을 잃은 참가자의 새 동작은 거절하고 완료 때 지급 대상에서도 제외한다.
- 혼자 및 도움 모드는 `STUDENT` 소유자만 점수 실행을 만들 수 있다. 교사 미리보기는 점수 대상이 없는 시범 실행으로 분리한다.
- 방 참가자는 공개 점수판과 자신의 지급 내역만 읽는다. 교사 방장은 현재 담당 범위 학생의 지급 결과만 읽을 수 있다.
- 혼자 및 도움 모드의 상태와 결과는 현재 소유자만 읽고, 소유자가 삭제된 실행은 만료 정리 외에는 읽을 수 없다.
- 결과 응답에는 원본 `state`, 숨은 카드와 물건, 내부 판정 사유, 다른 학생의 개인 활동을 넣지 않는다. 놀이 규칙상 공개가 필요한 검증 질문만 길이를 제한해 공개 상태에 포함한다.
- 참가자 표시 이름과 질문, 대답, 이야기 원문은 `GameActivity`에 저장하지 않는다. 진행에 필요한 원문은 활성 실행의 `state`에만 두고 실행을 닫을 때 제거하며, 감사 기록에는 내용 해시, 길이, 판정, 점수만 남긴다.
- 실행 상태, 활동 행, 점수 반영값은 서버 경로에서만 쓴다.
- 기존 방과 기존 점수 기록은 옮기거나 다시 계산하지 않는다. 실행 표지가 없는 이전 방은 현재처럼 점수 지급을 거부한다.
- 진행 중 실행은 마지막 활동 뒤 24시간에, 완료했지만 점수 기록이 없는 실행은 완료 뒤 30일에 `EXPIRED`로 바꾼다. 동작 경로도 `expiresAt`을 확인해 예약 작업 전에 기한이 지난 실행을 같은 거래에서 `EXPIRED`로 바꾸고 `409`를 반환한다.
- 확인 대기 실행은 30일이 지나면 남은 `PENDING` 기록을 `REJECTED`로 바꾸고 `SETTLED`로 닫는다. 확인 대기 기록이나 지급 기록이 연결된 실행과 활동은 계정 삭제 외에는 자동 삭제하지 않는다.
- 매일 서울 시각 오전 3시 30분에 `Authorization: Bearer <CRON_SECRET>`을 확인하는 `/api/cron/game-runs/cleanup`이 기한이 지난 실행 상태 변경, 오래된 확인 대기 실행 닫기, `EXPIRED` 뒤 7일이 지나고 점수 기록이 없는 실행의 물리 삭제를 수행한다. 한 묶음 100개, 한 예약 호출당 최대 10묶음으로 처리하며 각 묶음은 `FOR UPDATE SKIP LOCKED`로 골라 겹친 예약 실행도 같은 행을 처리하지 않는다.
- 점수 기록이 연결된 실행 삭제 시도는 외래 키가 거절해야 하며 정리 결과는 삭제 수, 확인 종료 수, 실패 수만 구조화 기록으로 남긴다.
- 데이터베이스 보안 검사에 `GameRun`, `GameActivity`, `SecurityEventBucket`의 공개 접근 차단을 추가한다.

### 경로와 거래

- `POST /api/question-games/runs`: 로그인 사용자와 모드, 참가자 범위를 확인하고 실행 생성
- `POST /api/question-games/runs/[id]/actions`: 놀이별 명령 검증, 활동 추가, 상태 및 버전 갱신
- `POST /api/question-games/runs/[id]/complete`: 완료 조건 확인
- `GET /api/question-games/runs/[id]/result`: 참가자에게 서버 점수 결과 반환

실행 생성과 완료를 포함한 모든 변경 요청은 `requestId`와 요청 지문을 사용한다. 같은 생성 요청은 기존 실행을 반환한다. 완료 요청은 `RUN_COMPLETE` 활동으로 기록해 아래 재전송 순서를 그대로 적용하고, 이미 확인 대기 또는 종료된 실행은 저장된 안전 응답을 반환한다.

실행 생성 거래는 다음 순서를 지킨다.

1. 소유자 사용자 행 잠금
2. 인증과 역할 확인
3. `(ownerId, creationRequestId)` 조회와 요청 지문 비교
4. 같은 지문이면 기존 실행 반환, 다른 지문이면 `409` 반환
5. 친구 모드이면 방 행 잠금과 방장·범위 확인
6. 진행 중 실행 수 확인
7. 새 실행 추가

재전송 조회는 진행 중 실행 수와 방 고유 제약보다 먼저 처리하므로 첫 응답을 받지 못한 성공 요청도 같은 실행을 돌려받는다.

각 활동 요청은 한 거래 안에서 다음 순서로 처리한다.

1. 실행 행 잠금
2. 인증 사용자, 실행 소유자 또는 참가자 권한 확인
3. 같은 `requestId` 활동 조회와 요청 지문 비교
4. 지문이 같으면 저장된 안전 응답 반환, 지문이 다르면 `409` 반환
5. 실행 상태와 화면이 보낸 버전 확인
6. 놀이별 명령 검증
7. 활동 추가와 실행 상태 갱신
8. 새 버전과 화면에 필요한 안전한 상태 저장 및 반환

완료 지급은 실행 잠금, 방장 또는 소유자 권한과 현재 범위 재확인, 완료 조건 확인, 활동 집계, 학생 행 잠금, `PointLog` 생성, 학생 합계 갱신, 실행 상태와 `settledAt` 기록을 한 거래 안에서 처리한다. 여러 학생을 갱신할 때는 학생 식별값 정렬 순서로 행을 잠가 교착을 막는다. 혼자 모드는 하루 30점, 도움 모드는 하루 50점, 친구 모드는 하루 120점으로 제한한다. `scoreDate`는 `completedAt`을 `Asia/Seoul` 날짜로 바꾼 값이며 거래 안에서 한 번만 고정한다.

상한 계산은 같은 `scoreDate`의 `PENDING`과 `APPROVED` 점수를 합쳐 남은 양을 구한다. 학생 방 완료는 남은 양 안에서 `PENDING` 점수를 예약하고 합계를 바꾸지 않은 채 실행을 `PENDING_APPROVAL`로 둔다. 담당 교사 승인 거래는 현재 범위를 다시 확인하고, 현재 승인 대상은 이미 예약 합계에 들어 있으므로 다시 더하지 않는다. 교사는 각 기록을 예약 점수보다 같거나 작게 줄일 수 있지만 늘릴 수 없다. 줄인 차이는 즉시 상한 예약에서 풀린다. 연결 기록이 모두 승인 또는 거절되면 실행을 `SETTLED`로 닫고 진행용 원문 상태를 비운다.

### 요청과 자료 한도

- 실행 생성은 사용자당 분당 10회, 동작은 분당 120회, 완료는 분당 10회, 결과 조회는 분당 120회로 제한한다.
- 한 사용자에게 진행 중 실행은 최대 3개다. 생성 거래에서 소유자 사용자 행을 먼저 잠근 뒤 진행 중 개수를 세어 동시 생성도 제한한다. 친구 방 참가자는 기존 제한인 최대 8명으로 둔다.
- 실행당 활동은 친구 모드 120개, 혼자 및 도움 모드 60개를 넘길 수 없다.
- `requestId`는 유효한 UUID 또는 64자 이하의 안전한 식별값만 받는다.
- 질문은 200자, 대답과 이야기는 500자, 명령 본문은 8킬로바이트, 서버 상태 직렬값은 64킬로바이트로 제한한다.
- 만료된 실행과 한도를 넘긴 명령은 상태를 바꾸지 않고 안정된 사유 코드와 함께 거절한다.

### 놀이별 서버 명령

- 질문 주사위: 서버가 주사위를 굴리고 현재 차례 학생의 질문만 기록
- 까바놀이: 서버가 문장 순서를 정하고 질문형 답안을 검사한 뒤 차례 전진
- 질문 사다리: 서버가 사다리와 배정을 만들고 학생별 한 질문만 기록
- 이야기 주사위: 서버가 단어를 선택하고 이야기, 질문, 대답 순서를 검사하며 학생 질문만 점수 반영
- 짝 찾기: 서버가 카드 순서와 짝 정보를 보관하고 두 카드 선택, 짝 판정, 점수, 다음 차례를 결정
- 이어 말하기: 기존 현재 차례 질문 추가와 같은 거래에서 활동 기록 추가
- 미스터리 상자: 숨은 물건을 서버 상태에만 보관하고 학생 질문 횟수와 완료를 기록

혼자 및 도움 모드는 같은 명령 처리기를 사용한다. 도움 모드에서 인공지능이 만든 질문이나 행동은 화면 진행에는 포함하지만 학생 점수에는 포함하지 않는다.

### 화면 전환

새 `useGameRun`이 실행 생성, 동작 요청 식별값, 버전 충돌 복구, 완료와 결과 조회를 담당한다. 놀이 구성 요소는 점수에 영향을 주는 동작을 로컬 상태에 먼저 확정하지 않고 서버 응답으로 갱신한다. 방 JSON은 대기실, 참가자, 화면 동기화와 장식 상태만 유지한다.

## 3단계: 핵심 흐름 화면 시험

새 `e2e/question-class-lifecycle.spec.ts`는 한 시험에서 교사와 학생 브라우저 문맥을 분리해 다음 순서로 실행한다.

1. 시험용 교사, 담당 학급, 학생, 저장된 탐구 설계 준비
2. 교사가 저장된 설계에서 질문수업 생성
3. 교사가 작성 요청을 보내 실제 알림 생성
4. 학생이 알림을 확인하고 질문 화면으로 이동
5. 학생 분류 호출만 고정 응답으로 바꾸고 실제 질문 저장
6. 교사가 질문 조회와 분석 화면 확인
7. 연결된 대기 포인트를 승인하고 학생 합계와 기록 상태를 데이터베이스에서 확인

실행마다 독립 학교와 식별 접두사를 사용한다. 정리는 알림, 분석, 포인트, 댓글과 좋아요, 번역, 질문, 수업, 설계, 담당 학급, 학생, 교사 순서로 수행한다.

`test:e2e:critical` 명령은 데스크톱 핵심 시험만 실행한다. 지속 검증에는 별도 작업을 추가하고 시험 데이터베이스 비밀값이 설정된 환경에서 매 푸시 실행한다. 태블릿 전체 묶음은 기존 선택 실행을 유지한다.

## 4단계: 보안 사건과 경보

`src/lib/security-events.ts`는 허용된 필드만 한 줄 구조화 기록으로 남긴다.

- 사건 이름, 심각도, 시각, 서버가 만든 요청 식별값
- 경로, 방식, 상태 코드
- 키 기반 해시로 바꾼 행위자, 인터넷 주소, 자료 식별값
- 사건별 아래 고정 목록에서 허용한 문자열 세부값

전자우편, 학교, 학년, 반, 번호, 질문 내용, 비밀번호, 가입 코드, 토큰, 원본 방 코드는 기록하지 않는다. 경로는 검색 문자열을 제거한 등록 경로 이름만 남긴다. 배포 환경의 인터넷 주소는 `VERCEL=1`일 때만 첫 `x-forwarded-for` 값을 신뢰하고, 그 밖에는 헤더값을 쓰지 않고 `unknown`을 사용한다.

해시는 전용 `SECURITY_EVENT_HASH_SECRET`을 사용한다. 배포 환경에서 이 값이 없으면 시작 검사를 실패시키며 `NEXTAUTH_SECRET`으로 대신하지 않는다. 개발과 시험에서만 고정된 비배포 기본값을 허용한다. 기록 실패는 원래 요청 결과를 바꾸지 않는다.

사건별 심각도와 허용 세부값은 코드의 고정 목록으로 제한한다.

- `api.rate_limited`, `warn`: `limitBucket`
- `auth.registration_code.rejected`, `warn`: 세부값 없음
- `access.cross_scope_denied`, `warn`: `resourceType`, `reasonCode`
- `game.room.nonmember_denied`, `warn`: `action`
- `game.room.host_action_denied`, `warn`: `action`
- `game.points.evidence_rejected`, `high`: `reasonCode`, `gameId`

정상 비밀번호 오입력, 정상 방 버전 충돌, 이미 처리된 같은 지문의 재전송은 보안 사건으로 세지 않는다. 서버 전용 `SecurityEventBucket`은 10분 단위 시작 시각, 사건 이름, 행위자 또는 인터넷 주소 해시, 허용된 범위 키, 횟수, 경보 시각만 보관하고 앞 네 값의 조합을 고유하게 둔다. 범위 키는 요청 제한 사건이면 `limitBucket`, 그 밖의 사건이면 고정값 `default`다. 사건 기록 때 같은 거래로 횟수를 올리며 가입 코드, 범위 밖 접근, 방 권한 거절은 5회, 요청 제한은 같은 제한 묶음 3회, 점수 증거 거절은 3회가 되는 순간 경보를 한 번 만든다. 묶음은 24시간 뒤 위 정리 예약 작업에서 삭제한다.

문턱값에 도달하면 `security.alert.threshold_reached` 구조화 기록을 남기고, 선택 `SECURITY_ALERT_WEBHOOK_URL`이 있으면 경보를 보낸다. 주소는 `https`만 허용하며 주소가 있을 때만 `SECURITY_ALERT_WEBHOOK_SECRET`을 필수로 검사한다. 본문은 기록 허용 필드와 전송 시각만 담고 전용 비밀값으로 `HMAC-SHA256` 서명한 `X-QBI-Signature: sha256=<hex>` 머리글을 붙인다. 응답을 반환한 뒤 프레임워크의 `after()`에서 보내며 전송 제한 시간은 1초, 재시도는 한 번이다. 실패는 구조화 오류 기록만 남기고 원래 요청을 실패시키지 않는다. 해시 비밀값과 경보 비밀값은 서로 다르게 설정한다.

## 오류 처리와 호환성

- 잘못된 명령과 입력은 `400`, 참가자 및 권한 위반은 `403`, 오래된 버전과 완료 상태 충돌은 `409`를 사용한다.
- 같은 `requestId`에 다른 명령 본문을 보낸 경우도 `409`를 사용하고 어떤 본문도 기록하지 않는다.
- 데이터베이스 직렬 처리 충돌은 최초 시도 뒤 최대 두 번 더 재시도한다. 재시도 전 20밀리초, 50밀리초에 0~10밀리초 흔들림을 더해 기다리고 이후 `409`를 반환한다. 입력, 권한, 버전 충돌은 재시도하지 않는다.
- 인공지능 실패는 검증 활동을 되돌리지 않으며 인공지능 보너스만 생략한다.
- 이전 화면이 실행 식별값 없이 점수를 요청하면 저장 없이 `409`와 새 화면 필요 사유를 반환한다.
- 새 표와 선택 열만 추가하므로 기존 자료 값과 기존 점수 합계는 바뀌지 않는다.

## 배포 방식

1. 새 표와 선택 열, 화면 가능 여부 정책, 보안 정책을 추가하되 모든 점수 기능은 비활성으로 시작한다.
2. 화면 정책을 먼저 배포해 거짓 실패와 가짜 결과 표시를 없앤다.
3. 공통 실행 기반과 이어 말하기 세로 단위를 완성하고 시험 통과 뒤 해당 기능만 `verified`로 연다.
4. 질문 주사위부터 미스터리 상자까지 같은 기준으로 한 단위씩 넓힌다.
5. 핵심 화면 시험과 보안 사건 기록을 활성화한다.
6. 각 단위마다 전체 시험, 린트, 타입 검사, 데이터베이스 검사, 제품 빌드 뒤 커밋하고 푸시한다.
