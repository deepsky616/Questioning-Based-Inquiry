# 게임 방 수명별 포인트 지급 설계

## 배경

게임 방 상태 저장은 `code`, `version`, `createdAt`을 함께 사용해 같은 네 자리 코드로 다시 만들어진 방을 서로 다른 수명으로 구분한다. 반면 게임 종료 포인트 지급은 아직 `gameId`와 표시용 `roomCode`만 중복 방지 기준으로 사용한다.

마지막 참가자가 나가 방 행이 삭제된 뒤 같은 코드와 같은 게임 종류의 새 방이 만들어지면, 새 방의 지급 요청이 이전 방의 포인트 기록을 찾을 수 있다. 이 경우 새 참가자는 포인트를 받지 못하고 이전 지급 내역을 현재 결과처럼 받을 수 있다.

## 목표

1. 새 처리기가 맡은 같은 방 수명의 재요청은 계속 한 번만 지급한다.
2. 같은 표시 코드라도 생성 시각이 다른 새 방은 독립적으로 지급한다.
3. 현재 방과 맞지 않는 오래된 지급 요청은 실제 포인트 쓰기 전에 거절한다.
4. 새 방식으로 만든 방은 완전한 수명 분리를 보장하고 기존 방은 예전 기록을 제한적으로 호환한다.
5. Prisma 스키마, 마이그레이션, 기존 포인트 합계와 기록을 바꾸지 않는다.
6. 지급 실패를 성공 결과처럼 방에 저장하지 않고 방장이 다시 시도할 수 있게 한다.

## 작업 경계

이번 작업에는 다음 항목을 포함하지 않는다.

- 학교, 학급, 교사, 학생 사이의 권한 경계 변경
- 포인트 정책과 지급 수치 변경
- 기존 포인트 기록의 일괄 수정이나 새 식별값 채움
- `PointLog` 열 또는 고유 제약 변경
- 게임 방 활동 임대, 자동 퇴장, 오래된 방 삭제
- 연습 문제 포인트의 중복 방지 키 변경

## 선택한 방식

현재 방 상태에서 이미 수명 식별값으로 쓰는 `createdAt`을 포인트 요청에도 전달한다. 서버는 표시 코드와 생성 시각으로 현재 방을 확인한 뒤, 기존 `PointLog.roomCode`에 내부 지급 키를 저장한다.

```text
표시 코드: 1234
생성 시각: 1783839000000
내부 지급 키: room:1234:1783839000000
```

이 방식은 새 열과 자료 옮김 없이 현재 고유 제약을 그대로 사용한다. `roomCode`는 최근 포인트 화면에 표시되지 않고 이미 연습 문제 중복 방지에서도 내부 키 저장 칸으로 쓰이므로, 접두어가 있는 방 지급 키와 충돌하지 않는다.

별도 무작위 `roomInstanceId` 열을 추가하는 방식은 의미가 더 분명하지만, 방과 포인트 표를 함께 바꾸고 정확히 채울 수 없는 기존 기록의 호환 정책도 필요하다. 현재 `createdAt`이 이미 방 저장 전체의 수명 경계이므로 이번에는 스키마 없는 단계적 방식을 선택한다.

새로 생성되는 `GameRoom` JSON에는 선택형 전환 표지 `pointAwardKeyVersion: 1`을 넣는다. 이 값은 새 지급 키를 이해하는 서버가 만든 방이라는 뜻이며 방 상태 저장의 객체 펼치기로 계속 보존된다. 기존 방에는 값을 채우지 않는다.

- 표지가 `1`인 새 방은 내부 지급 키 기록만 현재 수명 지급으로 인정한다.
- 표지가 없는 기존 방만 예전 표시 코드 기록을 제한적으로 확인한다.
- `GameRoom` 실행 시점 판별기는 표지가 없거나 정확히 `1`인 경우만 허용한다.

방을 읽는 공용 `loadGameRoom`과 지급 트랜잭션 안의 원시 행 조회는 같은 정규화와 `isGameRoom` 판별 순서를 사용한다. 배포 전 형식의 `version`이 없거나 `null`일 때만 먼저 `1`로 보정하고, 그 뒤 전체 방 자료를 판별한다. 표지에 알 수 없는 값이 있거나 그 밖의 필수 방 자료가 잘못된 행은 표지 없는 기존 방으로 낮춰 해석하지 않고 손상된 방으로 거절한다.

## 요청 계약

`RoomResult`는 기존 본문에 `roomCreatedAt`을 추가한다.

```ts
{
  gameId: game.id,
  roomCode: room.code,
  roomCreatedAt: room.createdAt,
  topic: room.topic,
  contributions,
}
```

`AwardRequest.roomCreatedAt`은 필수값으로 받는다.

- 유한한 음이 아닌 정수인지 검사한다.
- 현재 `GameRoom`의 코드, 게임 종류, 생성 시각이 모두 같은지 확인한다.
- 현재 방이 없거나 수명이 다르면 `409`로 거절하고 인공지능 호출과 포인트 쓰기를 하지 않는다.
- 값이 없는 이전 화면 요청도 `409`로 거절하고 새 화면으로 다시 열도록 안내한다.

수명값이 없는 요청을 표시 코드만으로 허용하면 코드 재사용 뒤 오래된 기여 자료가 새 방 포인트로 지급될 수 있다. 배포 중 열린 이전 화면 일부가 다시 열기를 요구하더라도 잘못된 지급보다 실패 후 복구를 우선한다.

## 중복 방지와 예전 기록 호환

표지가 `1`인 새 방은 `roomCode`가 새 내부 지급 키와 같은 기록만 현재 방의 기존 지급으로 본다.

표지가 없는 기존 방은 다음 두 종류의 기록을 확인한다.

1. `roomCode`가 새 내부 지급 키와 같은 기록
2. `roomCode`가 예전 표시 코드와 같고, 기록 생성 시각이 현재 방 생성 시각 이후인 예전 기록

두 번째 조건은 배포 전에 현재 방이 이미 포인트를 지급했지만 `awardResult` 저장이 실패한 경우의 이중 지급을 줄인다. 기존 서비스는 방 수명을 기록하지 않았으므로, 예전 요청이 늦게 끝나 기록 시각만 새 방보다 뒤가 되는 드문 경합은 기존 자료만으로 완전히 구분할 수 없다. 따라서 이 조건은 표지가 없는 기존 방에만 적용하는 최선 노력 호환이다.

새 서버가 만든 표지 방은 예전 표시 코드 기록을 무조건 무시하므로, 이전 방 요청이 늦게 예전 형식 기록을 만들더라도 새 방 지급을 막지 않는다. 수명 분리 보장은 표지가 있는 새 방부터 적용한다.

중복 확인, `P2002` 충돌 뒤 조회, 성공 뒤 생성은 모두 같은 지급 키 계산 도우미와 같은 조회 조건을 사용한다. 새 기록은 항상 내부 지급 키를 저장한다. `P2002` 뒤 조회 결과가 실제로 한 건 이상일 때만 기존 지급으로 응답하며, 빈 결과는 성공으로 바꾸지 않고 저장 실패로 처리한다.

현재 고유 제약은 학생과 보너스 종류까지 포함하므로 방 단위 잠금으로 사용할 수 없다. 서로 겹치지 않는 학생 목록을 담은 두 요청은 같은 방 수명이어도 모두 고유 제약을 통과할 수 있다. 이를 막기 위해 포인트 쓰기 트랜잭션 안에서 `gameId`와 내부 지급 키로 만든 PostgreSQL advisory transaction lock을 먼저 얻는다.

```text
lock key = gameId + ":" + internal award key
```

잠금을 얻은 뒤 기존 지급을 다시 확인한다. 첫 요청이 포인트를 썼다면 다음 요청은 학생 목록이 달라도 기존 지급 결과를 반환한다. 잠금은 트랜잭션이 끝나면 자동으로 풀리며 새 표나 영구 잠금 행을 만들지 않는다.

## 방 검증 순서

서버 처리 순서는 다음과 같다.

1. 요청 본문과 기여 목록 및 필수 `roomCreatedAt`을 정규화한다.
2. 표시 코드로 현재 방을 읽고 코드, 게임 종류, 생성 시각을 비교한다.
3. 현재 수명의 기존 지급 기록을 확인한다.
4. 기존 지급이면 기록을 반환하고 인공지능을 호출하지 않는다.
5. 새 지급이면 인공지능 분석을 트랜잭션 밖에서 실행한다.
6. 짧은 interactive transaction을 시작하고 방 수명 advisory lock을 얻는다.
7. 같은 트랜잭션에서 `game_rooms` 행을 공유 잠금으로 다시 읽어 코드, 게임 종류, 생성 시각을 재검증한다.
8. 현재 수명의 기존 지급을 다시 확인한다.
9. 여전히 새 지급일 때만 포인트 기록 생성과 사용자 합계 증가를 같은 트랜잭션에서 실행한다.

두 번째 방 검증과 포인트 쓰기 사이에는 해당 방 행의 공유 잠금을 유지한다. 이 짧은 구간에는 방 삭제와 코드 재사용이 끼어들 수 없다. 첫 검증 뒤 인공지능 호출 중 방이 바뀌면 두 번째 검증이 `409`로 끝내며 포인트는 쓰지 않는다.

동시에 들어온 두 새 요청은 인공지능 호출을 각각 수행할 수 있지만 advisory lock 뒤 한 요청만 포인트를 쓴다. 인공지능 호출까지 한 번으로 제한하려면 별도 예약 자료가 필요하므로 이번 스키마 없는 범위에는 포함하지 않는다.

트랜잭션 안의 두 번째 방 검증에서 생긴 `PointAwardError(409)`는 바깥 오류 처리에서 `500`으로 바꾸지 않고 그대로 전달한다. `P2002`만 현재 수명 기록 재조회 분기로 보내며, 그 밖의 자료 저장 오류는 기존처럼 `500`으로 정규화한다.

## 지급 결과 복원

포인트 응답이 유실되거나 방 결과 공유가 실패하면 같은 수명 요청이 기존 포인트 기록에서 결과를 복원해야 한다. 기본 지급 내역은 `PointLog` 행으로 복원하고, `bestQuestion`과 `summary`는 첫 새 기록의 기존 `aiAnalysis` 칸에 종류와 버전이 있는 짧은 JSON 결과로 저장한다.

```json
{
  "type": "game-room-award-result",
  "version": 1,
  "bestQuestion": {
    "studentId": "student-id",
    "question": "질문 내용",
    "reason": "선정 까닭"
  },
  "summary": "게임 전체 요약"
}
```

- 새 지급 트랜잭션은 첫 기록에만 결과 요약을 저장한다.
- 기존 지급 조회와 `P2002` 복구는 조회 순서에 기대지 않고 현재 수명의 모든 기록에서 종류, 버전, 내부 형식이 맞는 JSON을 찾아 `bestQuestion`과 `summary`를 함께 반환한다.
- 예전 기록처럼 값이 없거나 JSON이 아니면 지급 내역만 반환한다.
- 승인된 게임 포인트 기록에만 사용하며 연습 문제와 교사 검토 대기 기록의 `aiAnalysis` 의미는 바꾸지 않는다.

## 화면 실패 처리

현재 화면은 응답 상태를 확인하지 않고 모든 JSON 본문을 지급 성공처럼 저장하며 통신 오류도 조용히 버린다. 새 수명 검증에서 `409`가 생기면 오류 본문이 `awardResult`로 저장되어 재시도까지 막을 수 있다.

이를 다음처럼 바꾼다.

- `2xx`이며 지급 응답 형식이 맞을 때만 지역 결과와 방 `awardResult`를 갱신한다.
- `4xx`, `5xx`, 일반 글 본문, 통신 오류는 성공 결과로 저장하지 않는다.
- 방장에게 간단한 실패 문구와 포인트 지급 다시 시도 명령을 제공한다.
- 재시도는 같은 방 수명 키를 사용하므로 응답 유실 뒤 다시 눌러도 이중 지급하지 않는다.
- 다른 참가자는 기존처럼 방장 지급을 기다리며, 성공 결과가 방에 반영되면 함께 본다.
- 포인트 지급은 성공했지만 `onAction("update-state")`가 실패하면 지역 지급 결과는 유지하고 별도의 결과 공유 다시 시도 명령을 제공한다.
- 결과 공유 재시도는 포인트 API를 다시 호출하지 않고 이미 받은 결과만 방에 저장한다.
- 지급 요청을 시작할 때 `code`와 `createdAt`을 `awardRoom`으로 붙잡아 둔다. 최초 결과 공유와 공유 재시도는 모두 `onAction`의 `expectedRoom`으로 이 값을 넘기고 반환된 `ok`를 확인한다.
- 지급 처리 중 같은 표시 코드의 다른 수명으로 바뀌면 이전 결과 공유는 `superseded`로 끝나며 새 방 상태에는 쓰지 않는다.

## 자료 영향

Prisma 스키마와 마이그레이션은 바꾸지 않는다. 기존 `PointLog` 행과 사용자 포인트 합계도 일괄 수정하지 않는다.

배포 뒤 새 게임 방 JSON에는 `pointAwardKeyVersion: 1`이 들어가고, 새 지급 기록의 `roomCode` 값은 `room:<표시 코드>:<생성 시각>` 형식으로 저장된다. 첫 기록의 기존 `aiAnalysis`에는 응답 유실 복구를 위한 종류와 버전이 있는 결과 JSON이 들어갈 수 있다. 이는 정상 게임 생성과 완료 때 만들어지는 기존 JSON 및 포인트 기록이며 추가 자료 수집이 아니다. 예전 방과 기록은 그대로 두고 제한된 조회 호환 조건으로만 사용한다.

실제 연결 데이터베이스에는 시험 자료를 만들지 않는다. 방 조회, 포인트 기록, 인공지능 호출은 시험 대역으로 검증한다.

## 시험 설계

다음 동작을 실패 시험부터 고정한다.

1. `RoomResult`가 `roomCreatedAt`을 보낸다.
2. 같은 코드와 게임이라도 생성 시각이 다르면 새 지급으로 처리한다.
3. 같은 생성 시각의 재요청은 기존 지급을 반환한다.
4. 표지 없는 기존 방은 방 생성 뒤 만들어진 예전 표시 코드 기록을 중복으로 처리한다.
5. 표지 있는 새 방은 생성 시각이 더 늦은 예전 표시 코드 기록도 무시한다.
6. 현재 방이 없거나 게임 종류 또는 생성 시각이 다르면 `409`이고 쓰기와 인공지능 호출이 없다.
7. 겹치지 않는 학생 집합의 동시 요청도 방 수명 잠금 뒤 한 번만 지급한다.
8. 첫 방 확인 뒤 코드가 재사용되면 트랜잭션 안의 두 번째 확인이 `409`이고 쓰기가 없다.
9. 동시 지급의 `P2002` 뒤 현재 수명 기록과 저장된 결과 요약만 반환한다.
10. `RoomResult`는 실패 응답을 `awardResult`로 저장하지 않는다.
11. 포인트 지급 실패 재시도는 같은 수명 요청을 다시 보내며 성공 뒤에만 결과를 공유한다.
12. 포인트 성공 뒤 방 공유 실패는 포인트를 다시 지급하지 않고 공유만 재시도한다.
13. `roomCreatedAt`이 없는 이전 요청은 `409`이고 쓰기와 인공지능 호출이 없다.
14. 새 방 생성은 `pointAwardKeyVersion: 1`을 넣고 기존 방 판별은 표지 없음도 허용한다.
15. `version`이 없거나 `null`인 기존 방은 `1`로 보정해 읽고, 알 수 없는 표지나 그 밖의 잘못된 방 JSON은 기존 방으로 낮춰 처리하지 않고 거절한다.
16. 트랜잭션 안 수명 충돌의 `409`는 그대로 전달되고 `P2002` 뒤 빈 조회는 성공으로 응답하지 않는다.
17. 같은 생성 시각의 여러 기록에서 생성 순서와 무관하게 표지된 결과 JSON을 복원한다.
18. 지급 중 같은 코드가 다른 수명으로 바뀌면 최초 공유와 공유 재시도 모두 이전 결과를 새 방에 쓰지 않는다.

## 완료 기준

다음 조건을 모두 만족하면 작업을 마친다.

1. 표지 있는 새 방은 표시 코드 재사용과 예전 형식 기록의 시각에 상관없이 독립적으로 지급한다.
2. 표지 있는 방에 대한 새 처리기의 동시 요청과 재요청은 한 번만 지급한다.
3. 오래된 방 요청이 다른 수명의 포인트를 쓰지 못한다.
4. 기존 방의 최선 노력 기록 호환과 이전 화면 요청의 안전한 거절 시험이 통과한다.
5. 서로 다른 학생 목록의 동시 요청도 방 단위로 한 번만 지급한다.
6. 지급 결과와 방 공유 실패가 구분되고 각각 안전하게 다시 시도할 수 있다.
7. 전체 시험, 린트, 형 검사와 운영 빌드가 통과한다.
8. 데이터베이스 구조와 기존 자료에 차이가 없다.
9. 변경을 별도 커밋으로 만들고 원격 `main`에 푸시한다.
