# 게임 방 클라이언트 동기화 보완 설계

## 배경

게임 방 저장소와 요청 경로는 이미 `data.version`을 이용한 원자 저장을 사용한다. 서버는 같은 버전에서 시작한 두 저장 중 하나만 성공시키고, 충돌한 요청에는 최신 방을 담은 `409`를 반환한다.

남은 문제는 클라이언트의 응답 적용과 일부 게임 동작에 있다.

- `sendAction`은 렌더 시점의 `room.version`과 방 코드를 닫아 두므로, 같은 함수 참조로 동작을 이어서 호출하면 두 번째 요청이 이전 버전을 보낼 수 있다.
- 폴링, 성공 응답, `409` 응답이 도착한 순서대로 `room`을 덮어써서 낮은 버전의 늦은 응답이 화면을 과거로 되돌릴 수 있다.
- 방을 나가거나 다른 방으로 이동한 뒤 끝난 요청이 이전 방을 다시 화면에 넣을 수 있다.
- `409`에서도 방 객체를 반환하므로 호출부가 이를 성공으로 보고 사용자의 입력을 지울 수 있다.
- `actionLoading`이 불리언 하나라서 요청이 겹치면 먼저 끝난 요청이 아직 남은 요청의 적재 상태까지 끌 수 있다.
- 메모리 게임은 참가자별 주사위 한 칸이 아니라 `diceRolls` 전체를 일반 상태 갱신으로 보낸다. 두 참가자가 동시에 굴리면 한쪽 결과가 충돌하고, 실패한 참가자는 지역 상태 때문에 다시 굴릴 수도 없다.

## 목표

1. 모든 방 동작이 호출 순간의 최신 방 코드와 버전을 사용하게 한다.
2. 낮은 버전이나 이전 방 세대의 늦은 응답이 현재 화면을 되돌리거나 방을 되살리지 못하게 한다.
3. 동작 성공과 실패를 반환형에서 분명히 나누고, 실패 시 사용자 입력을 보존한다.
4. 겹친 요청이 모두 끝날 때까지 적재 상태를 유지한다.
5. 메모리 게임의 동시 주사위 결과를 참가자별로 안전하게 합친다.
6. 기존 원자 저장 계층을 재사용하고 데이터베이스 구조와 기존 자료를 바꾸지 않는다.

## 작업 경계

이번 작업에는 다음 항목을 포함하지 않는다.

- 학교, 학급, 교사, 학생 사이의 전반적인 권한 경계 변경
- Prisma 스키마, 데이터베이스 표, 보안 정책 변경
- 기존 방 자료의 일괄 보정이나 옮김 작업
- 폴링 주기 변경이나 실시간 통신 도입
- 모든 게임 동작을 서버 전용 명령으로 한꺼번에 바꾸는 작업
- 일반 `update-state` 또는 `set-state`의 자동 충돌 재시도
- 오래된 방 자동 정리와 만료 시간 도입
- 메모리 게임 외 초기화 흐름의 전면적인 재시도 화면 추가

## 선택한 방식

클라이언트의 최신 상태 참조와 단조 버전 적용을 먼저 보완하고, 서로 독립인 참가자 결과를 전체 지도 덮어쓰기로 처리하던 메모리 주사위만 서버 전용 명령으로 옮긴다.

클라이언트 요청 직렬화만으로는 다른 기기의 동시 요청과 폴링 경합을 해결하지 못한다. 모든 게임 동작을 서버 명령으로 옮기면 경계는 더 강해지지만 이번 문제에 비해 변경 범위와 회귀 위험이 크다. 따라서 현재 저장 계층과 화면 구조를 유지하면서 확인된 유실 경로만 닫는 단계적 방식이 가장 보수적이다.

## 공용 동작 결과 계약

`src/lib/question-games-data.ts`에 다음 의미의 공용 결과형을 둔다.

```ts
export type RoomActionResult =
  | { ok: true; room: GameRoom }
  | {
      ok: false;
      room: GameRoom | null;
      status: number | null;
      reason:
        | "conflict"
        | "missing"
        | "network"
        | "inactive"
        | "superseded"
        | "rejected";
    };
```

`sendAction`은 항상 이 형식을 반환한다.

- `2xx`와 유효한 방 응답은 `ok: true`다.
- `409`는 최신 방을 화면에 적용할 수 있어도 `ok: false`, `reason: "conflict"`다.
- `404`는 `reason: "missing"`이다.
- 그 밖의 HTTP 실패는 `reason: "rejected"`이며 실제 상태 코드를 보존한다.
- 통신 실패는 `status: null`, `reason: "network"`다.
- 활성 방이 없으면 요청하지 않고 `reason: "inactive"`를 반환한다.
- 요청 뒤 방 세대가 바뀌면 응답을 적용하지 않고 `reason: "superseded"`를 반환한다.

실패 결과의 `room`에는 응답에 포함되어 안전하게 적용된 최신 방 또는 현재 알고 있는 방을 담는다. 호출부는 방 객체의 존재 여부가 아니라 `result.ok`만으로 성공을 판정한다.

## 클라이언트 방 상태 흐름

`useRoom`은 React 상태와 함께 다음 동기식 참조값을 유지한다.

- `roomRef`: 현재 적용된 방
- `activeCodeRef`: 현재 활성 방 코드
- `roomGenerationRef`: 방 연결의 세대값
- `connectIntentRef`: 생성과 참가 중 가장 최근 연결 요청 번호
- `pendingActionCountRef`: 아직 끝나지 않은 변경 요청 수

방 코드와 방 객체를 바꾸는 내부 도우미는 참조값을 먼저 갱신한 뒤 React 상태를 갱신한다. 이렇게 해야 React가 다시 렌더되기 전 이어진 호출도 최신 값을 읽는다. 외부에 제공하는 `setActiveCode`도 원시 상태 설정기가 아니라 같은 참조값과 세대값을 함께 관리하는 래퍼로 둔다.

### 방 적용 규칙

모든 GET과 PATCH 응답은 공통 `applyRoom`을 거친다.

1. 방 생성과 참가 성공은 명시적인 강제 교체로 새 방을 적용한다.
2. 일반 폴링과 동작 응답은 현재 방 코드와 응답 방 코드가 같을 때만 적용한다.
3. 같은 방에서는 응답 버전이 현재 버전보다 낮으면 버린다.
4. 같은 버전 이상의 응답은 `roomRef`를 먼저 바꾸고 `setRoom`으로 화면 상태를 맞춘다.
5. 다른 방의 응답은 강제 교체가 아닌 한 버린다.

`applyRoom`은 적용 뒤 실제로 유지된 방을 반환한다. 따라서 성공 응답의 버전이 이미 적용된 더 높은 버전보다 낮더라도 서버 동작 자체는 성공으로 반환하되 호출부에는 현재의 더 높은 버전 방을 준다.

생성과 참가 요청은 각각 `connectIntentRef`의 새 번호를 잡는다. 가장 최근 번호와 일치한 성공 응답만 강제 교체할 수 있다. 이 번호는 기존 방의 폴링 세대를 바꾸지 않으므로 실패한 연결 시도가 현재 방의 폴링을 멈추지 않는다.

### 요청 세대 규칙

폴링과 방 동작은 시작 시점의 방 코드와 세대값을 기록한다. 응답을 적용하거나 오류를 표시하기 전에 현재 참조값과 다시 비교한다.

- 방을 나가거나 다른 방으로 바뀐 뒤 도착한 응답은 방과 오류 상태를 바꾸지 않는다.
- 나가기 성공 시 세대값, 활성 코드, 방 참조값을 동기적으로 먼저 바꾸고 화면 상태를 비운다.
- 현재 방의 `404`만 활성 방을 비운다. 이미 세대가 바뀐 `404`는 무시한다.
- `409`에 최신 방이 있으면 단조 버전 규칙으로 적용하지만 동작 결과는 실패로 유지한다.
- 통신 실패는 현재 방을 유지하고 현재 세대의 요청일 때만 오류를 보여준다.

`sendAction`은 렌더 당시 값을 의존값으로 닫아 두지 않는다. 호출 직전에 `activeCodeRef.current`와 `roomRef.current?.version`을 읽어 요청을 만든다. 일반 동작에는 `expectedVersion`을 넣되, 서버가 최신 상태에 다시 적용하는 `memory-roll`에는 사전 버전 거절을 사용하지 않는다.

### 겹친 요청의 적재 상태

각 변경 요청 시작 시 진행 수를 하나 올리고 `finally`에서 하나 내린다. `actionLoading`은 진행 수가 하나 이상일 때만 참이며 마지막 요청이 끝난 뒤에만 거짓이 된다. 폴링 조회는 사용자 변경 동작이 아니므로 이 수에 넣지 않는다.

## 호출부 동작

게임 구성 요소의 `onAction` 형식을 `Promise<RoomActionResult>`로 통일한다. 다음 입력은 `result.ok`가 참일 때만 비운다.

- 질문 릴레이의 주제와 질문
- 카바의 답안
- 질문 주사위의 질문
- 이야기 주사위의 이야기, 질문, 답안
- 질문 사다리의 질문

종료, 다시 시작, 단순 단계 이동처럼 지역 입력을 버리지 않는 호출은 결과를 의도적으로 무시할 수 있다. 이 경우 `void onAction(...)` 또는 명시적인 `await`를 사용해 성공을 잘못 추론하지 않게 한다.

이번 작업은 모든 게임 초기화 실패 화면을 새로 만들지 않는다. 다만 메모리 게임에서 확인된 영구 잠금 경로는 함께 고친다.

## 메모리 게임 주사위 명령

### 상태와 요청

메모리 게임의 `rolling` 상태에 `rollRoundId`를 추가한다. 방장이 카드 생성을 끝내고 `rolling` 단계로 들어갈 때 `crypto.randomUUID()`로 한 번 만들며, 같은 주사위 라운드의 모든 참가자가 같은 값을 사용한다. 이는 `gameState` 안의 일반 JSON 값이므로 데이터베이스 구조 변경이 아니다.

배포 전에 이미 `rolling` 단계였던 방은 `rollRoundId`가 없을 수 있다. 이때 클라이언트와 서버는 `legacy:<room.code>:<room.createdAt>` 형식의 같은 대체값을 계산한다. 첫 주사위 저장이 이 값을 `gameState`에 함께 넣고 이후 요청은 저장된 값을 사용한다. 대체값은 이 호환 경로에서만 허용하며 별도 일괄 보정은 하지 않는다.

클라이언트는 다음 요청만 보낸다.

```ts
{
  action: "memory-roll",
  roll: 1,
  rollRoundId: "..."
}
```

사용자 식별값은 요청에서 받지 않고 로그인 세션에서 구한다. `roll`은 1부터 6까지의 정수여야 하며 `rollRoundId`는 현재 방 상태의 값과 같아야 한다.

### 서버 처리

`memory-roll`은 일반 `expectedVersion` 사전 검사를 건너뛰고 기존 `saveGameRoom`의 원자 저장 결과를 이용해 최대 세 번 최신 방에 다시 적용한다.

각 시도는 다음 순서를 따른다.

1. 방의 게임 종류가 `memory`인지 확인한다.
2. 로그인 사용자가 현재 참가자인지 확인한다.
3. 메모리 상태, 주사위 값, 라운드 식별값을 확인한다. 비어 있거나 형식이 잘못된 값은 `400`, 형식은 맞지만 현재 라운드와 다른 값은 `409`다.
4. 같은 사용자에게 같은 값이 이미 있으면 저장 없이 성공 응답을 반환한다. 응답을 잃은 뒤 `play` 단계에서 다시 보낸 경우도 성공이다.
5. 같은 사용자에게 다른 값이 이미 있으면 처음 저장된 값을 지키고 `409`를 반환한다.
6. 기존 값이 없는데 현재 단계가 `rolling`이 아니거나 라운드가 바뀌었으면 최신 방과 `409`를 반환한다.
7. 최신 `diceRolls`에 현재 사용자 한 항목만 합친다.
8. 현재 참가자 모두의 결과가 모였으면 같은 저장 안에서 차례와 `phase: "play"`를 함께 정한다.
9. 원자 저장이 충돌하면 반환된 최신 방으로 같은 명령을 다시 계산한다.
10. 세 번 모두 충돌하면 마지막 최신 방과 `409`를 반환한다. 저장 중 방이 사라지면 `404`를 반환한다.

멱등 기준은 방 코드, `rollRoundId`, 로그인 사용자 식별값의 조합이다. 같은 값 재전송은 버전을 올리지 않으며, 다른 값 재전송은 처음 값을 바꾸지 않는다.

차례는 주사위 값 내림차순, 참가 시각 오름차순, 사용자 식별값 오름차순으로 정한다. 마지막 참가자의 결과와 차례 및 단계 전환이 한 번의 원자 저장에 들어가므로 별도 방장 효과는 제거한다.

아직 굴리지 않은 참가자가 `rolling` 단계에서 나가면 새 주사위 요청이 없을 수 있다. 기존 나가기 재시도 흐름도 참가자 제거 뒤 남은 참가자 모두에게 결과가 있는지 같은 규칙으로 다시 확인한다. 조건이 맞으면 참가자 제거, 차례 결정, `play` 전환을 같은 원자 저장에 넣는다. 저장이 충돌하면 기존 나가기 규칙대로 최신 방에서 참가자 제거와 완료 판정을 모두 다시 계산한다. 마지막 참가자 나가기는 기존처럼 방을 삭제한다.

### 응답과 오류

성공 응답은 최신 방과 다음 결과를 담는다.

```ts
{
  room,
  result: { roll, replayed }
}
```

- 메모리 게임이 아닌 방, 잘못된 주사위 값, 비어 있거나 형식이 잘못된 라운드 식별값: `400`
- 현재 참가자가 아님: `403`
- 방이 사라짐: `404`
- 라운드 변경, 잘못된 단계, 다른 값 재전송, 재시도 소진: 최신 방을 담은 `409`
- 손상되어 처리할 수 없는 메모리 상태나 예상하지 못한 저장 오류: `500`

## 메모리 화면 흐름

난이도 선택 뒤 첫 `generating` 저장이 성공해야만 인공지능 카드 생성을 시작한다. 실패하면 더 진행하지 않는다. 생성 잠금은 `try/finally`에서 반드시 풀고, 카드 생성 뒤 두 번째 동작은 최신 방 참조값의 버전을 사용한다.

주사위 애니메이션이 끝나면 일반 `update-state`가 아니라 `memory-roll`을 보낸다. 성공 전에는 서버 반영 완료로 확정하지 않는다. 실패하면 `diceLocal`과 지역 적재 상태를 풀어 사용자가 다시 시도할 수 있게 한다. 서버 방에 본인 결과가 반영되면 서버 값을 표시하며 다시 굴리기를 막는다.

모든 주사위가 모였는지 살피던 방장 전용 효과는 제거한다. 마지막 결과를 저장한 서버가 차례와 `play` 단계를 같은 버전에 확정한다.

## 시험 설계

실제 연결 데이터베이스에는 시험 자료를 쓰지 않는다. `fetch`, 인증, 저장소를 시험 대역으로 바꾸고 지연 응답을 직접 제어해 다음 동작을 검증한다.

### 클라이언트 동기화

1. 같은 `sendAction` 함수 참조를 두 번 이어 호출하면 두 번째 요청이 첫 응답의 새 버전을 보낸다.
2. 버전이 높은 동작 응답 뒤 도착한 낮은 폴링 응답이 방을 되돌리지 않는다.
3. 높은 버전의 `409`를 적용한 뒤 늦게 도착한 낮은 성공 응답을 버린다.
4. 방을 나간 뒤 끝난 PATCH 응답이 이전 방을 되살리지 않는다.
5. 다른 방으로 바뀐 뒤 이전 방의 GET과 PATCH 응답을 버린다.
6. `409`는 최신 방을 적용해도 `ok: false`를 반환한다.
7. `404`, 통신 실패, 활성 방 없음, 세대가 지난 응답의 이유와 상태 코드가 계약과 맞는다.
8. 겹친 두 요청 중 하나가 먼저 끝나도 다른 요청이 남아 있는 동안 `actionLoading`이 참이다.
9. 생성 뒤 참가와 참가 뒤 생성 응답 순서를 각각 뒤집어도 가장 최근 연결 요청만 방을 강제 교체한다.

### 입력과 메모리 화면

1. 각 입력 제출은 성공 때만 입력을 비우고 `409`나 통신 실패 때 값을 보존한다.
2. 메모리 카드 생성은 첫 단계 저장 실패 시 인공지능 요청을 보내지 않는다.
3. 메모리 생성 잠금은 성공과 실패 모두에서 풀린다.
4. 주사위 저장 실패 뒤 지역 주사위 상태가 풀려 다시 시도할 수 있다.
5. 방장 클라이언트의 별도 차례 확정 동작이 더 이상 실행되지 않는다.

### 메모리 주사위 서버 명령

1. 첫 원자 저장 충돌 뒤 최신 방에 다시 적용해 다른 참가자의 결과와 현재 결과를 모두 보존한다.
2. 같은 사용자와 라운드의 같은 값 재전송은 저장 호출과 버전 증가 없이 성공한다.
3. 같은 사용자와 라운드의 다른 값 재전송은 기존 값을 유지하고 `409`를 반환한다.
4. 마지막 참가자 결과가 차례, 현재 차례 번호, `play` 단계를 같은 저장에 넣는다.
5. 동점은 참가 시각과 사용자 식별값으로 늘 같은 순서가 된다.
6. 세 번의 저장 충돌 소진은 마지막 최신 방과 `409`를 반환한다.
7. 저장 중 방이 사라지면 `404`를 반환한다.
8. 잘못된 주사위 값, 참가자가 아닌 사용자, 다른 라운드, 잘못된 단계는 저장하지 않는다.
9. 응답 유실 뒤 `play` 단계에서 같은 값을 다시 보내도 성공한다.
10. 예전 `rolling` 상태는 정해진 대체 라운드 값을 첫 저장에 함께 넣고 이후 요청에서도 같은 값을 쓴다.
11. 아직 굴리지 않은 참가자가 나간 뒤 남은 참가자의 결과가 모두 있으면 나가기 저장이 차례와 `play` 단계를 함께 확정한다.
12. 잘못된 게임 종류와 손상된 메모리 상태를 각각 정해진 오류로 바꾸고 저장하지 않는다.
13. 요청 본문의 사용자 식별값은 무시하고 로그인 세션 사용자의 결과만 기록한다.
14. 예상하지 못한 저장소 예외는 오류 내용을 노출하지 않는 `500` 응답이 된다.

## 데이터 영향

Prisma 스키마와 데이터베이스 표를 바꾸지 않으며 기존 행을 일괄 읽거나 쓰지 않는다. `rollRoundId`는 새 메모리 주사위 라운드가 시작될 때 해당 방의 기존 `gameState` 저장과 함께 들어가는 값이다. 이는 사용자가 시작한 정상 게임 동작이며 별도 자료 옮김 작업이 아니다.

일반 게임 상태의 자동 재시도를 하지 않으므로 오래된 배열이나 지도가 최신 상태 위에 다시 덮이는 새 경로도 만들지 않는다.

## 검증 기준

다음 검사가 모두 성공해야 한다.

```bash
npm run lint
npx tsc --noEmit
npm test
npm run build
```

추가로 다음을 확인한다.

- Prisma 스키마와 데이터베이스 관련 설정 파일에 차이가 없다.
- 실제 연결 데이터베이스에 시험 자료를 만들거나 바꾸지 않았다.
- 낮은 버전 및 이전 세대 응답을 막는 시험이 시간 순서를 직접 제어한다.
- `409` 입력 보존 시험이 방 상태 갱신과 실패 결과를 함께 확인한다.
- 메모리 주사위 시험이 충돌 재적용, 멱등 재전송, 마지막 단계 전환을 각각 확인한다.
- 작업 트리에는 이번 범위와 무관한 변경이 없다.

## 되돌리기와 완료 기준

설계 문서와 구현을 나눠 커밋한다. 구현 문제가 생기면 구현 커밋만 되돌릴 수 있다. 스키마와 기존 자료를 바꾸지 않으므로 데이터 되돌리기 작업은 없다.

다음 조건을 모두 만족하면 작업을 마친다.

1. 방 동작이 호출 순간의 최신 코드와 버전을 사용한다.
2. 낮은 버전과 이전 방 세대 응답이 현재 방 상태를 바꾸지 않는다.
3. 모든 입력 제출이 `RoomActionResult.ok`로 성공을 판단한다.
4. 겹친 요청 동안 적재 상태가 일찍 꺼지지 않는다.
5. 메모리 주사위 동시 저장이 참가자별 결과를 잃지 않는다.
6. 같은 주사위 명령 재전송과 마지막 차례 확정이 멱등 규칙을 지킨다.
7. 전체 검사와 빌드가 통과한다.
8. 변경을 커밋하고 원격 `main`에 푸시한다.
