# 게임 방 동시 갱신 보완 설계

## 배경

현재 게임 방은 `game_rooms.data` 한 칸에 전체 방 상태를 JSON으로 저장한다. 각 방 상태에는 `version`이 있지만, `saveGameRoom`은 메모리 안의 버전만 하나 올린 뒤 방 코드만 조건으로 전체 JSON을 덮어쓴다.

두 요청이 같은 버전을 동시에 읽으면 둘 다 사전 검사를 통과할 수 있다. 먼저 저장한 요청의 결과를 나중 요청이 같은 다음 버전으로 덮어쓰므로 질문, 차례, 참가자, 방장 변경이 사라질 수 있다. 마지막 참가자 나가기도 방 코드만으로 삭제하므로, 그 사이 새 참가자가 들어온 최신 방을 지울 수 있다.

## 목표

1. 같은 버전에서 시작한 동시 저장은 정확히 하나만 성공하게 한다.
2. 저장 충돌 시 최신 방 상태를 클라이언트에 돌려준다.
3. 동시 참가와 나가기가 서로의 참가자 변경을 덮지 않게 한다.
4. 마지막 참가자 삭제가 더 최신인 방을 지우지 않게 한다.
5. 네 자리 방 코드가 동시에 겹쳐도 다음 후보로 다시 시도한다.
6. 데이터베이스 구조와 기존 행을 일괄 변경하지 않는다.

## 작업 경계

이번 작업에는 다음 항목을 포함하지 않는다.

- 학교, 학급, 교사, 학생 사이의 권한 경계 변경
- 별도 `version` 열 추가와 데이터베이스 옮김 작업
- 게임 규칙, 화면 구성, 최대 참가자 수 변경
- 폴링 주기 변경이나 실시간 통신 도입
- 여러 서버를 아우르는 요청 제한

## 선택한 방식

Prisma의 `updateMany`와 JSON 경로 비교를 사용한다. 저장 조건은 방의 기본 키인 `code`와 현재 JSON의 `data.version`을 함께 사용한다.

```ts
where: {
  code: room.code,
  data: {
    path: ["version"],
    equals: expectedVersion,
  },
}
```

PostgreSQL은 경쟁하는 갱신을 차례로 처리하고 실제 갱신 시점에 조건을 다시 확인한다. 먼저 저장한 요청이 버전을 올리면 나중 요청의 조건은 더 이상 맞지 않는다. 방 코드는 기본 키이므로 갱신 수가 `1`일 때만 성공이고 `0`이면 충돌 또는 삭제된 방이다.

JSON에 `version` 키가 없거나 값이 JSON `null`인 오래된 방은 현재 읽기 계약에 따라 버전 `1`로 본다. Prisma JSON 경로 비교는 이 두 경우를 버전 `1`로 찾지 못하므로, 기대 버전이 `1`일 때만 태그 기반 `$executeRaw`로 키 없음 또는 JSON `null` 조건을 다시 확인한다. 키 없음은 `data -> 'version' IS NULL`로, JSON `null`은 `data -> 'version' = 'null'::jsonb`로 구분한다. 보조 갱신은 `data`와 데이터베이스의 `updated_at`을 같은 시각으로 함께 바꾼다. 표와 열 이름은 고정하고 모든 값은 매개 변수로 전달한다. `$executeRawUnsafe`와 문자열 SQL 조립은 사용하지 않는다.

별도 버전 열은 형식이 더 또렷하지만 스키마 변경과 기존 자료 보정이 필요하다. 행 잠금은 원시 조회, 트랜잭션 대기, 연결 점유가 늘어난다. 현재 구조에서는 JSON 버전 조건부 갱신이 가장 작고 안전한 변경이다.

## 저장 계층 계약

`src/lib/game-room-store.ts`는 저장 성공, 충돌, 방 없음 상태를 호출부가 구분할 수 있는 결과를 반환한다.

저장 흐름은 다음과 같다.

1. 입력 방의 `version`을 기대 버전으로 잡는다.
2. 입력 객체를 직접 바꾸지 않고 새 방 복사본을 만든다.
3. 새 복사본의 `version`을 하나 올리고 `updatedAt`을 현재 시각으로 바꾼다.
4. `code`와 이전 JSON 버전을 조건으로 `updateMany`를 실행한다.
5. 기대 버전이 `1`이고 갱신 수가 `0`이면 버전 키 없음 또는 JSON `null`만 받는 안전한 보조 갱신을 실행한다.
6. 최종 갱신 수가 `1`이면 실제 저장된 새 방을 반환한다.
7. 최종 갱신 수가 `0`이면 방을 다시 읽는다. 방이 있으면 최신 방을 담은 충돌 결과를, 없으면 방 없음 결과를 반환한다.

입력 객체는 저장 성공 여부가 정해지기 전에 바뀌지 않아야 한다. 그래야 충돌 응답에 저장되지 않은 버전이나 변경 내용이 섞이지 않는다.

삭제도 같은 규칙을 쓴다. `deleteMany`에 `code`와 JSON 버전 조건을 함께 넣고 삭제 수를 확인한다. 기대 버전이 `1`인 오래된 방에는 버전 키 없음 또는 JSON `null`만 받는 보조 삭제를 적용한다. 최종 삭제 수가 `0`이면 최신 방을 다시 읽어 충돌과 이미 삭제된 상태를 구분한다. 기존처럼 삭제 오류를 모두 숨기지 않는다.

## 요청 처리 흐름

인증 뒤 요청 본문과 `action`을 먼저 읽은 다음 방을 조회한다. 방이 없고 동작이 `leave`이면 `{ room: null, deleted: true }`로 성공 처리하며, 그 밖의 동작은 기존처럼 `404`를 반환한다.

일반 게임 동작은 기존 `expectedVersion` 사전 검사를 빠른 거절 수단으로 유지한다. 그러나 최종 성공 판정은 반드시 저장 계층의 조건부 갱신 결과로 정한다. 사전 검사 뒤 다른 요청이 먼저 저장해도 조건부 갱신이 충돌을 잡는다.

다음 동작은 저장 충돌 시 최신 방과 오류 문구를 담아 `409`를 반환한다.

- `start`
- `update-state`
- `set-state`
- `next-turn`
- `set-topic`
- `add-question`
- `end`
- `restart`

조건부 저장 결과에서 방이 사라진 것이 확인되면 `404`를 반환한다. 성공 응답에는 메모리에서 바꾼 이전 객체가 아니라 저장 계층이 반환한 새 버전의 방을 담는다.

## 참가와 나가기

참가와 나가기는 같은 사용자의 요청을 최신 방에 다시 적용해도 결과가 같은 동작이다. 서버는 충돌할 때 최신 방을 기준으로 동작을 다시 계산하며 최대 세 번 시도한다.

참가는 매번 다음 순서로 조건을 다시 확인한다.

1. 같은 사용자가 이미 참가했다면 현재 방을 성공으로 반환한다.
2. 방이 대기 상태가 아니면 기존 오류를 반환한다.
3. 참가자가 여덟 명 이상이면 기존 정원 오류를 반환한다.
4. 참가자를 추가하고 조건부 저장한다.

이미 참가한 사용자의 참가 요청은 새로 저장하지 않고 현재 방을 성공으로 반환한다. 이미 방에 없는 사용자의 나가기 요청도 새로 저장하지 않고 성공으로 반환한다. 이 두 동작은 요청이 반복돼도 불필요하게 버전을 올리지 않는다.

나가기는 매번 최신 참가자 목록에서 사용자를 제거하고 방장 위임을 다시 계산한다. 마지막 참가자로 보일 때는 조건부 삭제를 시도한다. 그 사이 새 참가자가 들어와 삭제가 충돌하면 최신 방에서 나가기를 다시 계산하므로 새 참가자가 있는 방은 지워지지 않는다.

세 번 모두 충돌하면 최신 방과 `409`를 반환한다. 방이 이미 삭제된 상태에서 나가기는 목적이 이미 이뤄진 것으로 보고 성공 처리한다. 참가 중 방이 사라지면 `404`를 반환한다.

## 클라이언트 처리

일반 게임 동작은 현재처럼 `409` 응답의 최신 방을 화면 상태에 반영한다.

`leaveRoom`의 반환 계약을 `Promise<boolean>`로 바꾼다. 서버 응답을 확인해 성공일 때만 활성 방과 화면 상태를 비우고 `true`를 반환한다. `409` 응답에 최신 방이 있으면 활성 방 코드는 유지하고 그 방을 화면 상태에 반영한다. 네트워크 오류, 서버 오류, 재시도 소진이 생기면 현재 방을 유지하고 오류를 보여준 뒤 `false`를 반환한다. 화면 호출부도 `true`일 때만 방 선택 화면으로 이동한다.

참가는 서버가 재시도를 맡는다. 성공 전에는 활성 방을 설정하지 않으며, 실패하면 기존 참가 화면에서 서버 오류를 보여준다.

## 방 코드 생성

기존 흐름은 코드가 비었는지 먼저 조회하고 나중에 생성하므로, 두 요청이 같은 빈 코드를 고르면 한쪽이 고유 값 충돌로 실패한다.

각 후보 코드는 바로 생성한다. Prisma의 `P2002` 고유 값 충돌일 때만 다음 후보를 만들고, 그 밖의 데이터베이스 오류는 다시 시도 대상으로 숨기지 않는다. 최대 열두 후보가 모두 겹칠 때만 방 코드 생성 실패를 반환한다.

## 기존 자료 영향

Prisma 스키마와 `game_rooms` 표는 바꾸지 않는다. 현재 생성 코드는 모든 새 방에 `version: 1`을 저장하므로 일괄 보정이나 자료 옮김 작업은 없다.

버전 키가 없거나 JSON `null`인 오래된 방은 다음 정상 저장 때 보조 조건부 갱신을 거쳐 새 버전 형식으로 바뀐다. 이는 사용자가 요청한 방 변경과 함께 일어나는 같은 행의 정상 저장이며, 별도 일괄 변경은 아니다. 이미 숫자 버전이 있는 방에는 보조 갱신이 적용되지 않는다.

## 오류 응답 계약

- 사전 버전 불일치: 최신 방과 `409`
- 조건부 저장 충돌: 다시 읽은 최신 방과 `409`
- 저장할 방이 사라짐: `404`
- 참가와 나가기 재시도 소진: 최신 방과 `409`
- 이미 삭제된 방에서 나가기: `{ room: null, deleted: true }`와 성공
- 방 코드 고유 값 충돌: 다음 후보 재시도
- 그 밖의 데이터베이스 오류: 기존 오류 처리 경계로 전달

## 시험 설계

실제 연결 데이터베이스에는 시험 자료를 쓰지 않는다. 단위 시험은 조건부 갱신에 필요한 코드와 이전 버전 조건이 Prisma 호출에 함께 들어가는지, 그리고 각 반환 수를 저장 계층이 올바르게 해석하는지 검증한다. 실제 동시성 보장은 PostgreSQL의 원자적인 `UPDATE ... WHERE` 조건 재검사에 둔다.

1. `updateMany.count`가 `1`이면 버전이 하나 오른 새 방을 반환한다.
2. 저장 함수는 입력 객체를 직접 바꾸지 않는다.
3. `updateMany.count`가 `0`이면 최신 방을 다시 읽고 충돌을 반환한다.
4. 저장과 삭제 호출에는 `code`와 이전 JSON 버전 조건이 함께 들어간다.
5. 버전 키 없음과 JSON `null` 보조 저장은 기대 버전이 `1`일 때만 실행되며 `data`와 `updated_at`을 함께 바꾼다.
6. 조건부 삭제 성공, 충돌, 이미 삭제된 상태를 구분한다.
7. 각 일반 게임 동작의 저장 충돌은 최신 방을 담은 `409`를 반환한다.
8. 참가와 나가기는 충돌 뒤 최신 방에 동작을 다시 적용한다.
9. 이미 반영된 참가와 나가기 요청은 새 버전을 만들지 않고 성공한다.
10. 이미 삭제된 방의 나가기는 정해진 성공 응답을 반환한다.
11. 나가기 실패 시 클라이언트가 방 상태를 먼저 비우지 않는다.
12. 첫 방 생성이 `P2002`로 실패하면 다음 코드로 생성에 성공한다.
13. `P2002`가 아닌 생성 오류는 코드 겹침으로 잘못 처리하지 않는다.

기존 소스 문자열 검사만으로는 동시 갱신을 보장할 수 없으므로 저장 계층과 요청 경로를 직접 호출하는 동작 시험을 추가한다.

## 되돌리기와 완료 기준

설계 문서와 구현을 나눠 커밋한다. 구현 문제가 생기면 구현 커밋만 되돌릴 수 있어야 한다. 스키마와 기존 행을 바꾸지 않으므로 데이터 되돌리기 작업은 없다.

다음 조건을 모두 만족하면 작업을 마친다.

1. 모든 방 저장과 마지막 참가자 삭제가 JSON 버전 조건 또는 정해진 오래된 방 조건을 사용한다.
2. 저장과 삭제 시험이 코드와 이전 버전 조건, 성공, 충돌 분기를 검증한다.
3. 참가와 나가기가 충돌 시 최신 방을 기준으로 다시 계산된다.
4. 코드 겹침 오류가 다음 후보 생성으로 이어진다.
5. 클라이언트는 실패한 나가기를 성공처럼 처리하지 않는다.
6. 전체 검사와 빌드가 통과한다.
7. 변경을 커밋하고 원격 `main`에 푸시한다.
