# 질문놀이 진행과 동기화 보완 설계

## 배경

교사와 학생이 사용하는 질문놀이 일곱 가지는 같은 목록 자료와 같은 놀이 화면을 공유하지만, 화면 안내와 실제 방 규칙이 서로 다르다. 친구와 함께하는 방은 서버에서 최대 여덟 명으로 제한하면서 목록에는 최대 서른 명까지 표시되고, 한 명만 있어도 방장이 놀이를 시작할 수 있다.

놀이 종료 기준도 서로 다르다.

- 질문-대답 짝 찾기는 모든 짝을 찾으면 끝나지만 실패 카드 복원과 차례 넘김이 이전 참가자의 화면 시간에 의존한다.
- 이야기 주사위, 질문 주사위, 질문 릴레이와 질문 사다리는 목표 라운드가 없거나 방장의 수동 종료에 의존한다.
- 미스터리 박스는 친구 방에서도 참가자마다 별도의 지역 상태를 사용한다.
- 까바놀이는 자동 종료 수가 있으나 마지막 참가자가 방장이 아니면 종료 상태 저장이 거절될 수 있다.
- 혼자 및 인공지능 질문 사다리는 실제 질문을 작성하지 않아도 결과 공개만으로 완료와 점수 적립을 요청한다.

화면 주제 문제도 함께 존재한다. 놀이 화면에는 고정된 밝은 배경과 어두운 글자색이 인라인 스타일로 들어간 곳이 많다. 전역 어두운 화면 보정은 클래스만 바꾸므로 고정 인라인 색을 바꾸지 못한다. 질문 릴레이의 최신 질문, 이야기 주사위의 질문 흐름, 사다리 글자와 선이 대표적인 실패 경로다.

이번 작업은 보이는 문구만 고치는 것이 아니라 인원, 라운드, 차례, 종료, 공유 상태와 화면 대비를 같은 규칙으로 맞추는 작업이다.

## 목표

1. 친구와 함께하기의 참여 인원을 모든 놀이에서 두 명부터 여덟 명까지로 통일한다.
2. 일곱 놀이 모두 놀이 성격에 맞는 진행 단위와 자동 종료 조건을 갖게 한다.
3. 교사 목록, 학생 목록, 대기실과 실제 서버 검사가 같은 규칙 자료를 사용하게 한다.
4. 미스터리 박스의 비밀 물건, 질문, 대답, 차례, 점수와 결과를 모든 참가자가 같은 방 상태로 공유하게 한다.
5. 질문-대답 짝 찾기의 실패 복원과 다음 차례를 특정 참가자의 화면 생존 여부와 분리한다.
6. 질문 사다리의 이동 경로를 실제 사다리 규칙대로 그리고, 모든 모드에서 배정 주제로 질문을 작성하고 확인하게 한다.
7. 밝은 화면과 어두운 화면 모두에서 놀이의 본문, 상태, 카드와 그림을 읽을 수 있게 한다.
8. 기존 학생, 학급, 질문, 점수와 완료 기록을 바꾸거나 삭제하지 않는다.

## 제외 범위

- 웹소켓이나 별도 실시간 통신 서비스 도입
- 데이터베이스 표 또는 열 추가
- 학교, 교사와 학생 사이의 전반적인 권한 경계 변경
- 기존 질문과 점수의 일괄 보정
- 사용자가 만든 맞춤 놀이에 새 게임 엔진을 적용하는 작업
- 놀이의 교육 내용과 질문 유형 체계 전면 개편
- 기존 방 자료를 장기 보존 자료로 바꾸는 작업

## 검토한 방식

### 화면별 빠른 고침

각 화면에 종료 숫자와 어두운 화면 색을 직접 추가하고 미스터리 박스만 방 상태에 연결하는 방식이다. 변경량은 작지만 차례와 종료를 클라이언트가 계산하는 구조가 남는다. 마지막 참가자가 방장이 아닐 때의 종료 거절, 동시 제출 배열 덮어쓰기와 화면 이탈 뒤 멈춤을 반복해서 만들 수 있으므로 사용하지 않는다.

### 공통 규칙과 놀이별 서버 명령

참여 인원, 권장 시간, 진행 단위와 종료 목표를 공통 규칙 자료에 두고, 친구 방의 상태 변화는 놀이별 서버 명령이 판정한다. 기존 원자 저장과 버전 충돌 계약을 재사용할 수 있고 데이터베이스 구조를 바꾸지 않으면서 확인된 오류를 닫을 수 있다. 이번 작업에서 이 방식을 선택한다.

### 실시간 놀이 엔진 전면 재구축

모든 놀이를 사건 기록과 실시간 전송으로 다시 만들면 확장성은 높다. 그러나 저장 구조, 배포 방식, 재접속 계약과 운영 범위가 모두 달라지고 이번 오류 수정에 비해 변경 위험이 크므로 사용하지 않는다.

## 공통 놀이 규칙

새 공통 모듈 `src/lib/question-game-rules.ts`가 내장 놀이의 표시 규칙과 진행 목표를 소유한다. 한국어와 영어 목록 자료는 이 규칙을 바탕으로 참여 인원과 시간을 표시한다.

공통 규칙은 다음 의미를 제공한다.

- 친구 방 최소 인원: `2`
- 친구 방 최대 인원: `8`
- 목록 인원 문구: 한국어 `2~8명`, 영어 `2-8 players`
- 권장 시간 문구
- 진행 단위 이름과 목표
- 혼자, 인공지능, 친구 모드의 종료 정책
- 질문과 답안 최대 길이
- 친구 방에서 허용하는 점수 근거 수

참여 인원과 종료 목표는 화면에만 복사하지 않는다. 대기실 단추 상태, 방 시작 요청, 놀이 상태 판정과 목록 문구가 같은 규칙을 읽는다.

### 놀이별 진행과 시간

#### 질문-대답 짝 찾기

- 카드 두 장을 뒤집어 짝을 판정한 한 번을 한 차례로 센다.
- 쉬움은 여섯 짝과 최대 열여덟 차례, 보통은 열 짝과 최대 서른 차례, 어려움은 열다섯 짝과 최대 마흔다섯 차례를 사용한다.
- 모든 짝을 찾으면 남은 차례와 관계없이 조기 종료한다.
- 최대 차례에 도달하면 남은 짝을 공개하고 현재 점수로 종료한다.
- 짝을 맞힌 참가자는 같은 차례를 한 번 더 얻고, 틀리면 다음 참가자로 넘어간다.
- 목록 시간은 `약 5~20분`으로 표시한다.

#### 이야기 주사위

- 술래가 이야기 한 문장을 완성한 뒤 질문과 대답이 모두 저장돼야 한 묶음이 끝난다.
- 친구 모드는 술래를 제외한 각 참가자가 두 번씩 질문하고 술래가 모두 대답하면 자동 종료한다.
- 혼자와 인공지능 모드는 완결된 질문과 대답 세 묶음 뒤 자동 종료한다.
- 질문만 저장된 미완성 묶음은 종료 수에 포함하지 않는다.
- 목록 시간은 `약 5~20분`으로 표시한다.

#### 질문 주사위

- 모든 참가자가 한 번씩 주사위를 굴리고 질문을 확정하면 한 라운드가 끝난다.
- 세 라운드를 진행하며 전체 목표는 `참가자 수 곱하기 3`개의 질문이다.
- 혼자와 인공지능 모드도 학생 질문 세 개를 확정하면 결과 화면으로 이동한다.
- 목록 시간은 `약 5~15분`으로 표시한다.

#### 질문 사다리

- 사다리 배정, 학생 질문 작성, 질문 확인과 확정이 모두 끝나야 한 라운드가 끝난다.
- 혼자, 인공지능과 친구 모드 모두 세 라운드를 진행한다.
- 친구 모드는 해당 라운드의 활성 참가자가 모두 질문을 확정하면 다음 라운드로 자동 이동한다.
- 세 번째 라운드 마지막 확정 뒤 자동 종료한다.
- 목록 시간은 `약 10~15분`으로 표시한다.

#### 질문 릴레이

- 모든 참가자가 앞 질문과 연결된 질문을 한 번씩 확정하면 한 라운드가 끝난다.
- 세 라운드를 진행하며 전체 목표는 `참가자 수 곱하기 3`개의 질문이다.
- 질문 모양, 중복과 현재 차례를 서버가 확인한다.
- 목록 시간은 `약 5~15분`으로 표시한다.

#### 미스터리 박스

- 질문 또는 추측 한 번을 한 라운드로 센다.
- 최대 스무 라운드를 진행한다.
- 정답 추측은 즉시 성공 종료한다.
- 틀린 추측은 즉시 실패 종료하지 않고 한 라운드를 사용한다.
- 혼자 모드는 같은 학생이 다음 라운드를 계속하고, 인공지능 모드는 인공지능 친구에게, 친구 모드는 다음 참가자에게 차례를 넘긴다.
- 스무 번째 라운드까지 맞히지 못하면 정답을 공개하고 종료한다.
- 목록 시간은 `약 8~15분`으로 표시한다.

#### 까바놀이

- 친구 모드는 모든 참가자가 한 문제씩 바꾸면 한 라운드가 끝나고 세 라운드를 진행한다.
- 전체 목표는 `참가자 수 곱하기 3`문제이며 최소 여섯 문제다.
- 혼자와 인공지능 모드는 기존처럼 열 문제를 진행한다.
- 목록 시간은 `약 5~15분`으로 표시한다.

### 시간 계산 근거

목록 시간은 준비와 결과 확인 시간을 포함한 수업 활동 시간 범위다.

- 질문-대답 짝 찾기: 카드 한 차례를 약 십오 초부터 이십오 초로 보고 최대 열여덟 차례부터 마흔다섯 차례, 카드 준비와 결과 확인을 합쳐 약 오 분부터 이십 분으로 잡는다.
- 이야기 주사위: 이야기 준비에 약 이 분, 완결된 질문과 대답 한 묶음에 약 사십오 초부터 칠십오 초가 걸린다고 본다. 두 명은 두 묶음, 여덟 명은 열네 묶음이므로 약 오 분부터 이십 분으로 잡는다.
- 질문 주사위와 질문 릴레이: 여섯 개부터 스물네 개의 학생 질문을 하나당 약 이십 초부터 삼십오 초로 보고 준비와 결과 확인을 합쳐 약 오 분부터 십오 분으로 잡는다.
- 질문 사다리: 주제 준비에 약 이 분, 세 라운드의 배정과 동시에 진행하는 질문 작성 및 확인에 라운드당 약 이 분부터 삼 분, 결과 확인에 약 일 분을 더해 약 십 분부터 십오 분으로 잡는다.
- 미스터리 박스: 최대 스무 활동을 하나당 약 이십 초부터 삼십 초로 보고 준비, 단서 검토와 결과 공개를 합쳐 약 팔 분부터 십오 분으로 잡는다.
- 까바놀이: 여섯 문제부터 스물네 문제를 하나당 약 십오 초부터 삼십 초로 보고 준비와 결과 확인을 합쳐 약 오 분부터 십오 분으로 잡는다.

## 친구 방 시작과 호환 처리

대기실은 한 명일 때 시작 단추를 비활성화하고 두 명 이상이라는 안내를 보여 준다. 서버의 `start` 동작도 다시 인원을 확인한다. 화면을 우회한 한 명 시작 요청은 `400`으로 거절한다. 참가 요청의 여덟 명 상한은 기존 서버 검사를 유지하고 공통 규칙 값을 읽게 바꾼다.

새 방의 `gameState.stateVersion`에는 버전 `2`를 둔다. 시작된 옛 방에서 상태 버전이 없거나 현재 계약과 맞지 않으면 임의 변환을 시도하지 않는다.

방이 실제 놀이를 시작할 때 서버가 `GameRoom.playId` 최상위 필드에 새 실행 식별값을 한 번 만든다. `playId`는 같은 방 코드 안에서 다시 시작한 서로 다른 놀이 실행을 구분하고, 한 실행의 모든 라운드에서 유지된다. 각 놀이의 `roundId`는 `gameState` 안에 두고 라운드마다 새로 만들며 실행 식별값을 대신하지 않는다. 점수 지급, 다시 시작과 결과 화면 수명 판정은 모두 다른 위치를 추측하지 않고 이 두 위치만 읽는다.

- 대기 중인 옛 방은 정상적으로 새 규칙으로 시작할 수 있다.
- 진행 중인 옛 방은 안전한 호환 안내를 표시하고 방장에게 대기실에서 다시 시작하도록 한다.
- 옛 상태를 새 점수 근거로 사용하지 않는다.
- 방 코드는 유지하되 다시 시작할 때 이전 실행 상태와 최상위 `playId`, `pointEvidenceVersion`, `pointAwardKeyVersion`을 비우고 다음 시작에서 새 실행 식별값, 점수 근거 버전과 새 상태를 만든다. 첫 실제 라운드를 만들 때 새 `roundId`를 넣는다.

방 상태는 임시 놀이 자료이므로 별도 일괄 자료 이전을 하지 않는다.

진행 중인 옛 방의 호환 화면에는 기존 방장 전용 `restart` 동작을 사용하는 `새 규칙으로 다시 시작` 단추를 둔다. 방장이 누르면 같은 방 코드와 참가자 목록을 유지한 채 대기 상태로 돌아간다. 다른 참가자는 방장이 다시 시작할 때까지 기다리거나 방을 나갈 수 있다. 조회 요청 자체가 방 상태를 몰래 바꾸지는 않는다.

## 서버 명령 구조

친구 방의 실제 놀이 변경은 일반 `update-state`로 참가자가 임의 배열을 덮어쓰지 않게 한다. `src/lib/question-game-room-engine.ts`에 순수한 명령 판정기를 두고 요청 경로는 인증, 방 조회, 버전 확인, 원자 저장과 응답 변환을 맡는다.

판정기는 다음 입력을 받는다.

- 현재 방
- 로그인 참가자 식별값
- 명령 이름
- 검증된 명령 자료
- 현재 시각

판정기는 저장을 직접 하지 않고 다음 가운데 하나를 반환한다.

- 변경된 다음 방
- 이미 같은 동작이 반영된 멱등 성공
- 방 변경 없이 화면이 사용할 명령 결과
- 잘못된 입력
- 현재 차례나 참가자 조건 위반
- 오래된 라운드 또는 단계 충돌
- 손상된 상태

새 방 생성은 공통 규칙에 등록된 일곱 내장 놀이 식별값만 허용한다. 명령 요청도 이름이 현재 `room.gameId`의 허용 명령 목록에 있는지 먼저 확인한다. 맞춤 놀이는 이번 친구 방 엔진 대상이 아니며 내장 놀이 명령을 사용할 수 없다.

요청 경로는 로그인과 현재 방 참가 여부를 먼저 확인한 뒤 기존 `expectedVersion`과 방 생성 시각 경계를 확인한다. 참가자가 아닌 요청에는 최신 방을 담지 않은 `403`만 반환한다. 같은 네 자리 코드가 나중에 다른 방에 재사용돼도 예전 참가자가 새 방의 참가자나 상태를 충돌 응답으로 볼 수 없어야 한다.

원자 저장이 충돌하면 현재 참가자에게만 비공개 값을 제거한 최신 방을 담은 `409`를 반환하고 클라이언트가 최신 상태를 적용한다. 서버 명령은 유효한 마지막 활동이 종료 조건을 충족하면 활동 저장과 `status: "ended"`를 같은 저장에 넣는다. 이 자동 종료는 방장 여부와 관계없이 서버가 판정할 수 있다.

성공 응답은 `{ ok: true, room, result? }` 모양으로 통일한다. `RoomActionResult`의 선택 `result`에는 명령별로 검증된 짧은 응답 자료만 담고, `useRoom.sendAction`은 이를 버리지 않고 호출 화면에 반환한다. 첫 사용처인 실패 카드 복원 대기는 `result.retryAfterMs`를 영 이상 정수로 읽는다. 방 자료와 결과 자료는 모두 같은 공개 응답 직렬화를 거친다.

모든 놀이 엔진 상태 변경 명령과 `start`, `restart`는 클라이언트가 만든 `commandId`를 보낸다. 실행이 시작된 뒤의 명령은 현재 `playId`도 보내고, 실제 라운드 안에서 일어나는 명령은 현재 `roundId`까지 보낸다. 아직 라운드가 없는 `start`와 초기 준비 명령은 `expectedVersion`과 방 생성 시각을 확인하되 존재하지 않는 `roundId`를 요구하지 않는다. 종료 뒤 점수 결과 공개 명령은 `playId`만 확인하고 끝난 라운드의 식별값에 의존하지 않는다. 참가와 나가기는 기존 사용자 식별값 기반 중복 방지 계약을 유지하며 놀이 명령 목록에는 넣지 않는다.

실행 상태는 최근 처리한 명령 식별값을 정해진 개수만 보존한다. 같은 명령 식별값이 이미 반영됐으면 버전을 올리지 않고 현재 공개 방을 성공으로 반환한다. 예상 버전이 오래됐더라도 현재 실행에 같은 명령 식별값이 있으면 멱등 성공으로 처리하고, 없으면 최신 방과 `409`를 반환한다. 제출 성격의 명령은 참가자 식별값과 라운드 식별값으로 같은 자리의 중복도 별도로 막는다.

최근 명령 식별값 목록은 라운드가 바뀔 때 비우지 않고 한 `playId` 안에서 최대 예순네 개를 순환 보존한다. 그래야 라운드를 끝낸 마지막 명령의 응답이 유실돼도 다음 라운드에서 재전송을 멱등 성공으로 처리할 수 있다. 목록에서 밀려난 오래된 명령은 현재 라운드와 단계 검사를 통과하지 못하면 `409`로 끝나며 활동을 다시 반영하지 않는다. 명령 식별값은 놀이 점수 근거가 아니며 참가자 입력을 신뢰하는 수단으로 사용하지 않는다.

`restart`는 실행 상태와 명령 목록을 지우므로 상태 기반 멱등 규칙을 따로 둔다. 방장이 같은 방 생성 시각에 다시 요청했을 때 이미 `waiting`이고 최상위 `playId`, 두 점수 버전과 `gameState`가 비어 있으면 버전을 올리지 않는 성공을 반환한다. 따라서 첫 응답이 유실돼도 두 번째 요청이 새 실행을 만들거나 오류를 내지 않는다. `start`는 새 `gameState`의 최근 명령 목록에 자기 `commandId`를 남겨 일반 멱등 규칙을 따른다.

`commandId`는 영문 소문자로 바꾼 뒤 `xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx` 모양의 서른여섯 바이트 고유 식별값만 허용하며, `y` 자리는 `8`, `9`, `a`, `b` 가운데 하나여야 한다. `playId`, `roundId`와 `revealId`는 서버만 만든다. 명령 본문은 유티에프 팔 기준 육십사 킬로바이트, 직렬화한 `gameState`는 백이십팔 킬로바이트, 전체 `GameRoom`은 백육십 킬로바이트를 넘을 수 없다. 한국어 최대 길이의 카드 열다섯 쌍을 담아도 허용하면서 무제한 방 상태 증가는 막는 값이다. 서버 명령은 다음 공통 크기 제한과 놀이별 배열 상한도 저장 전에 확인한다.

- 주제와 짧은 단어: 각각 팔십 자 이내
- 학생 질문: 이백 자 이내
- 이야기와 대답: 각각 오백 자 이내
- 생성 카드 질문: 이백 자 이내
- 생성 카드 대답: 오백 자 이내
- 생성 단어 한 개: 육십 자 이내
- 질문-대답 짝: 난이도에 따른 여섯, 열 또는 열다섯 쌍만 허용
- 전체 직렬화 방 상태: 백육십 킬로바이트 이내

안전 상한을 넘은 요청은 저장하지 않고 `400`으로 거절한다. 클라이언트가 보내지 않은 인식할 수 없는 필드는 버린다.

상태 버전 `2`인 일곱 내장 놀이에서는 `update-state`, `set-state`, `next-turn`, 일반 `set-topic`과 일반 `add-question`을 참가자와 방장 모두 사용할 수 없다. 초기 준비, 주제 설정, 단계 이동, 질문 및 답안 제출, 차례 이동, 종료와 결과 공유를 모두 이름이 정해진 서버 명령으로 처리한다. 옛 상태 버전에서 새 활동을 계속 받지 않고 호환 화면의 `restart`와 `leave`만 허용한다.

종료 뒤 점수 분석 결과를 다른 참가자에게 보여 주는 흐름은 `publish-award-result` 명령으로 분리한다. 클라이언트는 결과 본문을 보내지 않고 현재 `playId`만 보낸다. 서버는 현재 실행 식별값, 완료 종료 상태와 교사 방장 권한을 확인한 뒤 실행별 점수 키로 실제 `PointLog`를 조회한다. 적립 기록과 그 안에 저장된 분석 결과 스냅샷을 기존 복원 함수로 다시 만든 경우에만 `awardResult` 한 필드를 저장한다. 기록이 없거나 참가 학생 범위를 벗어난 기록, 클라이언트가 덧붙인 결과 필드가 있으면 요청을 거절한다. 놀이 활동, 차례, 점수, 종료 사유와 라운드 자료는 바꾸지 못한다.

### 초기 상태와 난수

방 시작은 게임 종류에 맞는 버전 `2` 기본 상태를 서버에서 만든다. 내용 생성이 필요한 놀이는 준비 단계로 시작하고 방장이 검증된 준비 명령을 보낸 뒤 실제 놀이 단계로 이동한다.

- 질문-대답 짝 찾기의 질문과 대답 내용은 기존 이중 언어 생성과 대체 자료를 사용할 수 있지만, 카드 식별값과 배치는 서버가 섞는다.
- 이야기 주사위의 단어 묶음은 기존 이중 언어 생성과 대체 자료를 사용하고, 실제 주사위 결과는 서버가 고른다.
- 질문 주사위의 눈은 서버가 고른다. 클라이언트가 최종 숫자를 요청 자료로 보내지 않는다.
- 질문 사다리의 발판과 배정은 서버가 만든다.
- 미스터리 박스의 비밀 물건은 서버가 고른다.
- 까바놀이의 문장 순서는 서버가 섞는다.
- 질문 릴레이의 주제는 방장이 입력하지만 길이와 허용 형식을 서버가 검사한다.

클라이언트 애니메이션은 결과를 미리 확정하지 않는다. 서버가 저장한 결과를 받은 뒤 같은 값을 보여 주며, 통신 실패 시 임의 지역 결과를 놀이 기록으로 남기지 않는다. 시험에서는 고정 난수 공급자를 판정기에 넣어 결과를 재현할 수 있게 한다.

공유 내용은 가능한 한 언어와 무관한 의미값 또는 한국어와 영어를 함께 가진 자료로 저장한다. 미스터리 박스 대답은 `yes`, `no`, `unknown` 의미값으로 저장하고 각 화면이 현재 언어로 표시한다. 질문 언어는 명령의 `locale`을 `ko` 또는 `en`으로 제한해 서버 판정에 사용한다.

### 참가자 이탈

나가기 저장은 참가자 제거와 방장 위임뿐 아니라 현재 놀이 상태도 함께 정리한다.

- 현재 차례 참가자가 나가면 다음 활성 참가자로 이동한다.
- 저장된 차례 순서에서는 이탈한 식별값을 제거한다. 이탈자가 현재 차례보다 앞에 있으면 현재 번호를 하나 줄여 같은 참가자의 차례를 유지하고, 이탈자가 현재 차례면 제거 뒤 같은 번호에 온 다음 참가자를 현재 차례로 삼는다. 번호는 남은 참가자 수로 나눈 범위 안에 둔다.
- 라운드 완료 대상은 라운드 시작 참가자와 현재 참가자의 교집합으로 다시 계산한다.
- 이탈로 남은 제출이 모두 충족되면 다음 라운드 또는 자동 종료를 같은 저장에 넣는다.
- 이야기 주사위의 술래가 나가면 다음 활성 참가자를 술래로 정하고 미완성 질문과 대답 묶음만 버린다. 이미 완결된 묶음은 보존한다.
- 놀이 시작 뒤 활성 참가자가 한 명보다 적으면 기존 규칙대로 방을 삭제한다.
- 놀이 시작 뒤 활성 참가자가 한 명만 남으면 `insufficient-players` 사유로 결과를 종료하고 완료 점수는 주지 않는다.
- 비밀 물건과 질문 기록처럼 결과 화면에 필요한 자료는 남기되 새 활동은 받지 않는다.
- 방장 이탈 뒤 기존 규칙대로 가장 먼저 참가한 활성 참가자에게 방장을 넘기고, `hostId`와 참가자별 `isHost`가 정확히 한 명을 가리키게 한다. 놀이 역할과 방장 역할은 별도로 계산한다.

이 정리는 놀이별 순수 도우미를 사용하며 나가기 원자 저장이 충돌하면 최신 방에서 참가자 제거와 상태 정리를 함께 다시 계산한다.

## 질문-대답 짝 찾기 상태 흐름

짝 찾기는 기존 주사위 명령과 같은 서버 판정 방식을 카드 놀이까지 확장한다.

공용 상태는 다음 의미의 값을 가진다.

- 단계와 난이도
- 카드와 질문-대답 짝
- 실행 및 라운드 식별값과 차례 순서
- 현재 차례 번호
- 획득한 카드
- 현재 공개된 카드
- 참가자별 점수
- 사용한 차례와 최대 차례
- 실패 공개 식별값과 복원 마감 시각
- 마지막으로 복원한 실패 공개 식별값

### 카드 뒤집기

`memory-flip` 명령은 서버에서 다음을 확인한다.

1. 현재 단계가 카드 놀이인지 확인한다.
2. 로그인 사용자가 현재 차례인지 확인한다.
3. 획득했거나 이미 공개된 카드인지 확인한다.
4. 첫 카드는 질문, 두 번째 카드는 대답이라는 순서를 확인한다.
5. 첫 카드면 공개 상태만 저장한다.
6. 두 번째 카드면 서버가 짝을 판정하고 사용 차례를 하나 늘린다.
7. 짝이면 카드, 점수와 조기 종료 여부를 같은 저장 후보에 넣는다.
8. 실패면 두 카드를 공개한 채 고유한 `revealId`와 `resolveAt`을 저장한다.

### 실패 복원

`memory-resolve-miss` 명령은 `revealId`를 받고 다음을 보장한다.

- 복원 마감 전 요청은 현재 상태와 함께 서버 시각으로 계산한 `retryAfterMs`를 반환한다.
- 마감 뒤 첫 유효 요청만 공개 카드를 닫고 다음 차례로 이동한다.
- 같은 식별값 재전송은 이미 처리된 성공으로 응답한다.
- 이전 참가자가 화면을 닫아도 다른 참가자가 같은 명령을 보낼 수 있다.
- `lastReveal` 제거에는 `undefined` 대신 직렬화 가능한 `null` 또는 필드 없는 새 상태를 사용한다.

복원 뒤에는 `lastReveal: null`과 함께 `lastResolvedRevealId`를 남긴다. 현재 공개 실패가 없을 때 이 값과 같은 복원 요청은 멱등 성공이고, 다른 이전 식별값은 최신 방과 `409`를 반환한다. 새 실패가 생기면 `lastResolvedRevealId`는 유지하고 새 `lastReveal.revealId`를 별도로 기록한다.

클라이언트는 기기 시각으로 `resolveAt`을 계산하지 않고 서버가 응답한 `retryAfterMs`만큼 기다린 뒤 다시 요청한다. 값은 영 이상 복원 대기 상한 이하로 제한한다. 같은 버전의 방 조회 응답은 방 객체를 다시 적용하지 않아 시간을 초기화하지 않는다.

## 미스터리 박스 공유 흐름

새 `RoomMysteryBox` 화면을 방 놀이 지도에 등록한다. 지역 `MysteryBoxGame`은 혼자와 인공지능 모드만 맡는다.

공용 상태에는 다음 값만 참가자에게 공개한다.

- 상태 버전과 라운드 식별값
- 단계와 현재 라운드 및 최대 라운드
- 참가자 차례 순서와 현재 차례
- 질문, 대답과 추측 기록
- 참가자별 점수
- 승자와 종료 뒤 공개된 정답

숨은 물건은 서버 저장 방에는 유지하되 진행 중 응답에서는 제거한다. 공통 방 응답 직렬화 함수가 정상 응답, 폴링, 충돌 응답과 오류 응답 모두에서 비공개 값을 제거해야 한다. 종료 전에는 물건 이름, 분류, 속성이나 이를 복원할 수 있는 난수값을 보내지 않는다.

비공개 값은 저장된 방의 `gameState.private` 아래에만 두고, 클라이언트가 보내는 상태 자료에서 이 이름을 받지 않는다. 공개 응답 직렬화는 원본 방을 직접 바꾸지 않고 복사본에서 `private`을 제거한다. 방 생성, 참가, 조회, 모든 명령 성공, `409`, 나가기와 다시 시작 응답이 이 직렬화를 공통으로 사용한다.

친구 모드의 숨은 물건은 서버가 검증할 수 있는 내장 물건 목록에서 고른다. 인공지능 키가 없어도 놀이를 시작하고 대답할 수 있어야 한다.

각 내장 물건은 한국어와 영어의 정답 이름, 허용 별칭과 다음 불리언 속성을 가진다.

- 생물, 동물, 식물
- 먹을 수 있음
- 작음, 큼
- 색이 다양함
- 주로 실내에 있음
- 다리가 있음, 날 수 있음
- 사람이 만듦
- 단단함, 젖어 있음, 둥금

질문 판정은 현재 언어의 정해진 표현 사전에서 속성을 찾는다. 정확히 한 속성을 찾으면 해당 값으로 `yes` 또는 `no`를 정하고, 지원하는 부정 표현이 정확히 하나 있으면 결과를 뒤집는다. 인식한 속성이 없거나 둘 이상이거나 부정 범위가 모호하면 `unknown`으로 답한다. `unknown`도 한 라운드를 사용하며 화면은 더 단순한 질문을 하도록 안내한다. 서버는 자유 입력을 인공지능에 보내 정답을 추론하지 않는다.

추측은 유니코드 정규화, 앞뒤 공백 제거, 연속 공백 축약과 영어 소문자 변환을 거친다. 정규화한 값이 정답 이름 또는 허용 별칭 전체와 정확히 같을 때만 성공한다. 부분 문자열과 한 글자 일치는 허용하지 않는다.

### 명령

- `mystery-start`: 방장만 새 라운드 식별값과 서버 비공개 물건을 만든다.
- `mystery-ask`: 현재 참가자의 예 또는 아니오 질문을 검사하고 서버가 답을 판정한다.
- `mystery-guess`: 현재 참가자의 추측을 판정한다. 정답이면 종료하고 틀리면 라운드만 늘린다.

서버는 질문 모양과 이백 자 제한, 현재 차례, 중복, 라운드 식별값과 최대 라운드를 검사한다. 스무 번째 활동이 실패하면 같은 저장에서 정답을 공개하고 종료한다. 재접속한 참가자는 기존 질문과 현재 차례를 그대로 이어받는다.

## 질문 사다리 구조

`src/lib/question-ladder.ts`에 생성, 경로 추적과 화면 경로 계산을 맡는 순수 함수를 둔다. 혼자 화면과 방 화면은 같은 함수를 사용한다.

### 사다리 생성 규칙

- 참가자는 두 명부터 여덟 명까지다.
- 한 높이에서 서로 맞닿는 가로 발판을 만들지 않는다.
- 모든 시작점은 하나의 도착점에 도달하며 전체 도착은 일대일 순열이어야 한다.
- 경로는 시작점, 각 높이의 세로 이동, 실제 가로 발판 이동, 다음 세로 이동을 순서대로 보존한다.
- 화면에는 기본 세로선과 가로 발판을 중립색으로 그리고 선택한 실제 경로 하나만 강조한다.
- 시작 세로선 전체를 강조하거나 대각선으로 도착점을 잇지 않는다.

### 모드별 흐름

- 혼자 모드는 학생이 고른 시작점의 배정 주제로 질문 하나를 작성한다.
- 인공지능 모드는 학생과 인공지능 친구가 각자 배정 주제를 받고 학생 질문과 인공지능 예시 질문을 나란히 보여 준다.
- 친구 모드는 각 참가자가 자기 실제 경로, 배정 주제와 전체 제출 현황을 본다.

배정 공개 뒤 흐름은 `질문 작성 -> 질문 확인 -> 고쳐 쓰기 또는 확정 -> 다음 라운드`로 통일한다.

질문은 먼저 현재 언어의 질문 모양과 이백 자 제한을 검사한다. 서버의 확정 명령은 같은 검사와 기존 경량 비속어 검사를 다시 실행한다. 이 두 검사가 강제 경계다.

기존 질문 분류 요청은 열린 정도, 질문 유형과 도움말을 보여 주는 학습 보조로 사용한다. 사실적 질문도 놀이 목적에 맞을 수 있으므로 자동 실패로 막지 않는다. 분류 결과가 부적절하다고 판단하면 화면은 고쳐 쓰기를 권하지만, 서버의 보안 판정은 클라이언트가 보낸 분류 결과를 신뢰하지 않는다.

분류 요청이 실패하거나 호출 제한에 걸리면 입력을 보존하고 `다시 확인`과 `도움말 없이 확정`을 함께 제공한다. 질문 모양, 길이와 서버 비속어 검사를 통과한 질문은 외부 서비스 장애와 관계없이 확정할 수 있어 친구 방 전체가 멈추지 않는다.

친구 모드의 `ladder-submit-question` 명령은 현재 `roundId`, 로그인 사용자, 배정 주제, 질문 모양, 길이와 같은 라운드 중복 제출을 다시 확인한다. 마지막 참가자 확정은 다음 라운드 상태 또는 세 번째 라운드 종료 상태를 같은 저장에 넣는다. 라운드 시작 참가자가 나간 경우 완료 대상은 시작 참가자와 현재 참가자의 교집합으로 계산한다.

## 나머지 놀이의 자동 종료

이야기 주사위, 질문 주사위, 질문 릴레이와 까바놀이도 클라이언트가 `status: ended`를 직접 보내지 않는다.

- 이야기 주사위 명령은 이야기, 질문과 대답 단계를 검사하고 완결된 묶음 수로 종료한다.
- 질문 주사위 명령은 현재 차례의 굴림과 질문 확정을 나누어 검사하고 세 라운드 마지막 질문에서 종료한다.
- 질문 릴레이는 기존 `add-question` 서버 판정을 확장해 목표 질문 수와 현재 라운드를 계산하고 마지막 질문에서 종료한다.
- 까바놀이는 현재 문장, 질문 모양과 참가자 차례를 검사하고 마지막 답안을 저장하면서 종료한다.

각 놀이 상태는 `round`, `maxRounds` 또는 놀이에 맞는 목표 수, `roundId`와 누적 활동을 가진다. 화면에는 현재 진행과 전체 목표를 항상 보여 준다.

방장에게는 적어도 한 라운드가 완결된 뒤에만 `놀이 일찍 마치기`를 제공한다. 확인 창을 거쳐 `endReason: "host"`로 종료하며 결과는 볼 수 있지만 참가, 질문, 완료, 우승과 인공지능 보너스를 포함한 어떤 점수 지급도 요청하지 않는다. 목표를 모두 채운 종료는 `endReason: "completed"`, 참가자 부족 종료는 `endReason: "insufficient-players"`로 구분한다.

## 화면 주제와 읽기 쉬움

놀이 구성 요소는 공통 의미 색을 사용한다.

- 놀이 카드 배경: `bg-card`
- 기본 본문: `text-foreground`
- 보조 본문: `text-muted-foreground`
- 일반 테두리: `border-border`
- 입력 배경: `bg-background` 또는 `bg-secondary`
- 옅은 상태 배경: 화면 주제에 맞는 공통 상태 구성 요소

참가자 강조색과 놀이 대표색은 구분과 장식에만 사용한다. 긴 본문 글자에 대표색을 직접 쓰지 않으며, 대표색 위 단추 글자는 충분한 대비를 가진 전경색을 사용한다. 비활성 차례는 고정 회색 인라인 스타일 대신 보조 배경과 보조 글자 토큰을 사용한다.

계산 대비 통과 기준은 일반 글자와 입력 글자에서 최소 `4.5:1`, 큰 글자와 핵심 놀이 선 및 상태 경계에서 최소 `3:1`로 둔다. 색만으로 차례, 성공과 실패를 구분하지 않고 글자나 익숙한 표시를 함께 제공한다.

질문 릴레이 최신 질문과 이야기 주사위 흐름의 고정 본문색을 제거한다. 방 결과의 최고 질문 영역도 밝고 어두운 화면 각각에서 명시적인 전경색을 갖게 한다.

사다리 그림의 기본 선과 글자는 화면 주제 변수에서 가져온다. 실제 경로 강조색은 어두운 화면에서도 배경과 구분되는 팔레트를 사용한다. 그림 글자를 다섯 글자에서 자르기만 하지 않고 긴 주제는 그림 아래 배정 영역에서 전체 내용을 볼 수 있게 한다.

교사 미리보기와 학생 실제 놀이는 같은 공용 구성 요소를 사용하므로 공용 수정으로 두 페이지를 함께 보완한다.

## 점수와 완료 근거

기존에 적립된 점수와 완료 기록은 바꾸지 않는다. 새 규칙은 배포 뒤 새로 시작한 놀이에만 적용한다.

- 혼자와 인공지능 모드는 현재 서버에 진행 근거가 없으므로 점수 지급 요청을 보내지 않는다. 실제로 확정한 학생 질문 수는 결과 화면의 활동 수로만 보여 준다.
- 배정 공개, 카드 뒤집기나 인공지능 예시만으로 질문 점수를 주지 않는다.
- 학생이 방장인 친구 방은 점수 지급 요청을 보내지 않고 놀이 결과만 보여 준다. 점수 분석 실패 화면도 보여 주지 않는다.
- 교사가 방장인 친구 방만 기존 담당 학생 범위 검사를 거쳐 서버에 저장된 활동을 점수 근거로 사용할 수 있다. 클라이언트는 사용자 역할로 불필요한 요청을 막고 서버는 방장 역할과 담당 범위를 다시 검사한다.
- 질문 사다리 세 라운드는 학생당 최대 세 질문, 여덟 명 방에서 최대 스물네 질문을 허용하도록 점수 정책과 검증을 함께 맞춘다.
- 질문 주사위와 릴레이도 참가자당 세 질문이라는 새 목표와 현재 점수 상한이 충돌하지 않는지 함께 검사한다.
- 완료 종료한 미스터리 박스와 짝 찾기는 놀이별 성공 조건과 실제 활동 수를 서버 근거로 기록한다.
- 미스터리 박스는 서버 검증 대상 놀이에 추가하고 학생당 질문 스무 개, 방 전체 질문 스무 개를 절대 상한으로 둔다. 추측은 질문 점수에 넣지 않는다.
- 질문 사다리의 같은 문장 검사에는 라운드 식별값을 포함해 서로 다른 라운드의 유효한 확정을 구분하되, 같은 라운드 중복은 거절한다.
- `endReason`이 `completed`가 아닌 친구 방은 결과 화면만 보여 주고 어떤 점수 지급도 요청하지 않는다.

### 실행별 점수 식별값

상태 버전 `2` 실행을 시작할 때 `pointEvidenceVersion: 2`와 `pointAwardKeyVersion: 2`를 함께 설정한다. 점수 서비스는 다음을 모두 확인해야 한다.

- 방의 `playId`와 요청의 `playId`가 같은지
- `gameState.stateVersion`과 `pointEvidenceVersion`이 모두 `2`인지
- 방 상태가 종료이고 `endReason`이 `completed`인지
- 놀이별 목표와 서버 저장 활동이 서로 맞는지
- 요청 사용자가 교사 방장이며 참가 학생이 담당 범위 안인지

실행별 점수 키는 기존 `PointLog.roomCode` 문자열에 `room:<방 코드>:<방 생성 시각>:<playId>` 형식으로 저장한다. 표나 열은 바꾸지 않는다. 점수 요청, 자문 잠금, 기존 지급 조회와 고유 값 충돌 복구가 모두 이 키를 사용한다.

결과 화면의 수명 키도 방 코드와 생성 시각뿐 아니라 `playId`를 포함한다. 방장이 대기실로 돌아가 같은 방에서 새 놀이를 시작하면 이전 지급 결과, 지역 오류, 자동 지급 시도와 공유 결과를 재사용하지 않는다.

옛 점수 근거 버전 `1`의 기록과 조회 계약은 기존 기록 복원에만 유지한다. 새 엔진 실행은 반드시 버전 `2` 경로를 사용하며 상태 버전이 없거나 일반 상태 변경으로 만들어진 자료는 새 점수 근거로 받지 않는다. `GameRoom` 검증 형식은 두 점수 버전을 읽을 수 있게 하되, 버전 `2` 지급 조건을 별도로 엄격하게 검사한다.

### 놀이별 점수 근거

- 질문 릴레이와 질문 주사위: 서버가 저장한 확정 질문만 학생별 최대 세 개로 센다.
- 질문 사다리: 누적 확정 질문을 `roundId`와 참가자 식별값으로 구분해 학생별 최대 세 개로 센다.
- 까바놀이: 서버가 질문 모양으로 판정해 저장한 답안만 학생별 최대 세 개로 센다.
- 이야기 주사위: 학생이 만든 질문만 질문 활동으로 세고 술래의 대답과 이야기 문장은 질문 수에 넣지 않는다.
- 미스터리 박스: 서버가 저장한 예 또는 아니오 질문만 세고 추측은 질문 수에 넣지 않는다.
- 질문-대답 짝 찾기: 서버가 판정한 획득 짝 수를 활동 점수로 사용하되 질문 작성 수로 표시하지 않는다.

점수 근거에서 학생이 실제로 작성한 질문 수는 `validQuestions`, 놀이 안의 승패 계산용 값은 `activityScore`로 분리한다. 두 값은 서버가 방 상태에서 만들고 클라이언트가 보낸 수를 신뢰하지 않는다. 질문-대답 짝 찾기의 `validQuestions`는 항상 영이고 획득 짝은 `activityScore`에만 들어간다. 획득 짝 자체에는 질문 작성 점수나 별도 활동당 점수를 주지 않고, 서버가 `activityScore`로 판정한 우승자에게만 기존 우승 보너스를 적용한다. 따라서 새 점수 종류나 자료 이전은 필요하지 않다.

참가와 완료 점수는 완료 종료한 교사 방에만 적용한다. 우승 보너스는 경쟁 규칙이 분명한 질문-대답 짝 찾기와 까바놀이에만 적용하고, 이야기 주사위, 질문 주사위, 질문 사다리, 질문 릴레이와 협력형 미스터리 박스에는 적용하지 않는다. 우수 질문과 질문 관련 인공지능 보너스도 실제 학생 질문이 있는 놀이에만 적용한다.

완료 조건과 우승 조건은 분리한다. 질문-대답 짝 찾기가 최대 차례를 모두 사용했지만 아무도 짝을 얻지 못했거나 까바놀이의 저장된 시도를 모두 틀린 경우도 목표 시도 수를 채웠으므로 `completed`다. 교사 방이면 서버가 저장된 시도 수로 완료를 확인해 참가와 완료 점수는 지급하되, 최고 `activityScore`가 영이면 우승자를 만들지 않고 우승 보너스도 지급하지 않는다. 영 점수를 활동 근거 없음으로 잘못 거절하지 않는다.

서버 검증 대상 목록은 새 엔진 명령으로 근거를 저장하는 놀이만 포함한다. 각 놀이의 상한, 완료 조건과 근거 읽기 시험이 준비되지 않은 상태에서는 목록에 추가하지 않는다.

옛 상태 버전의 방 활동은 새 완료 근거로 인정하지 않는다.

## 오류 처리

- 친구 방 한 명 시작: `400`
- 여덟 명을 넘는 참가 요청: `400`
- 로그인되지 않은 요청: `401`
- 방 참가자가 아닌 사용자: `403`
- 현재 차례가 아닌 사용자: `409`와 최신 방
- 이전 라운드 식별값 또는 이전 방 생성 시각: `409`와 최신 방
- 이미 반영된 같은 명령: 저장 없이 멱등 성공
- 손상된 놀이 상태: 세부 자료를 노출하지 않는 `500`
- 방 없음: `404`
- 인공지능 확인 실패: 학생 입력과 현재 라운드를 유지하고 다시 시도 가능
- 상태 버전 `2`에서 일반 상태 덮어쓰기 요청: `403`
- 옛 상태 버전에서 놀이 활동 요청: `409`와 다시 시작 안내

오류 응답의 방 자료도 미스터리 박스 비공개 값을 제거해야 한다.

## 시험 설계

구현은 실패하는 시험을 먼저 추가하고 해당 시험을 통과하는 최소 변경 순서로 진행한다. 실제 연결 데이터베이스에는 시험 자료를 쓰지 않는다.

### 공통 규칙과 방 시작

1. 일곱 놀이의 한국어와 영어 인원 문구가 친구와 함께 두 명부터 여덟 명까지를 나타낸다.
2. 교사 목록과 학생 목록이 같은 규칙 자료를 사용한다.
3. 한 명 방은 화면과 서버에서 시작하지 못한다.
4. 두 명과 여덟 명 방은 시작할 수 있다.
5. 아홉 번째 참가자는 서버에서 거절된다.

### 서버 명령과 자동 종료

1. 각 놀이가 목표 직전에는 진행 중이고 마지막 유효 활동과 종료를 같은 저장 후보에 넣는다.
2. 마지막 활동자가 방장이 아니어도 활동, 점수와 종료가 함께 저장된다.
3. 현재 차례가 아닌 참가자와 이전 라운드 요청은 상태를 바꾸지 않는다.
4. 같은 명령 재전송은 활동과 차례를 중복 증가시키지 않는다.
5. 동시 요청 가운데 충돌한 요청은 최신 방을 받고 입력을 보존한다.
6. 참가자 이탈 뒤에도 남은 활성 참가자를 기준으로 라운드를 끝낼 수 있다.
7. 상태 버전 `2`의 참가자와 방장 모두 일반 상태 덮어쓰기로 활동, 차례, 점수와 종료 사유를 바꾸지 못한다.
8. 처리된 `commandId` 재전송은 버전을 올리지 않고 성공하며 최근 명령 목록은 예순네 개를 넘지 않는다.
9. 현재 차례보다 앞, 현재 차례와 뒤의 참가자가 각각 나갈 때 다음 활성 참가자가 정확하다.
10. 등록되지 않은 놀이 식별값으로 방을 만들 수 없고 현재 방과 다른 놀이의 명령은 거절된다.
11. 형식이나 길이가 잘못된 `commandId`, 육십사 킬로바이트를 넘는 명령, 백이십팔 킬로바이트를 넘는 놀이 상태와 백육십 킬로바이트를 넘는 방은 저장되지 않는다.
12. 시작과 초기 준비는 아직 없는 `roundId` 없이 진행되지만 실행 중 활동은 맞는 `playId`와 `roundId`를 모두 요구한다.
13. 다시 시작 응답이 유실된 뒤 같은 요청을 보내면 비어 있는 대기 방을 저장 없이 성공으로 반환한다.
14. 명령별 성공 `result`를 `RoomActionResult`와 `useRoom.sendAction`이 화면까지 그대로 전달한다.

### 질문-대답 짝 찾기

1. 카드 순서, 짝과 현재 차례를 서버가 판정한다.
2. 실패 뒤 같은 방 상태가 이 초마다 다시 그려져도 처음 마감 시각 뒤 차례가 한 번만 넘어간다.
3. 실패 복원 담당 참가자가 화면을 닫아도 다른 참가자가 복원할 수 있다.
4. 두 복원 요청이 겹쳐도 한 차례만 이동한다.
5. 방장이 아닌 참가자가 마지막 짝을 맞혀도 종료된다.
6. 모든 짝 조기 종료와 난이도별 최대 차례 종료를 각각 검사한다.
7. 같은 버전의 방 조회가 화면 시간을 다시 시작하지 않는다.
8. 기기 시각이 서버보다 빠르거나 느려도 서버의 `retryAfterMs`를 사용해 한 번만 복원한다.

### 미스터리 박스

1. 두 참가자 화면에 같은 질문, 대답, 차례와 라운드가 보인다.
2. 비밀 물건은 시작과 진행 응답, 충돌 응답에 나타나지 않는다.
3. 현재 차례가 아닌 질문과 추측은 거절된다.
4. 틀린 추측은 즉시 끝나지 않고 다음 참가자에게 넘어간다.
5. 정답 추측은 조기 종료하고 정답을 공개한다.
6. 스무 번째 실패 활동은 한 번만 종료한다.
7. 재접속은 기존 라운드를 이어받고 새 물건을 만들지 않는다.
8. 정상 응답, 폴링, `409`, 나가기와 다시 시작 응답에 비공개 물건 자료가 없다.
9. 혼자 모드의 첫 틀린 추측은 다음 학생 라운드로 이어지고 스무 번째 실패 활동에서만 종료된다.
10. 인공지능과 친구 모드의 틀린 추측은 다음 활성 참가자에게 차례를 넘긴다.

### 질문 사다리

1. 두 명부터 여덟 명까지 같은 높이의 맞닿는 가로 발판이 없다.
2. 시작별 도착점이 일대일 순열이고 배정 주제와 같다.
3. 강조 경로는 실제 가로 발판만 지나고 대각선이나 여분 세로선이 없다.
4. 혼자와 인공지능 모드는 결과 공개 뒤 질문 입력을 보여 준다.
5. 질문 아닌 문장과 이백 자 초과를 거절한다.
6. 인공지능 확인 실패 뒤 입력을 유지하고 다시 시도한다.
7. 질문을 고쳐 쓴 뒤 확정할 수 있다.
8. 세 번째 라운드 전에는 완료나 점수를 요청하지 않는다.
9. 친구의 동시 제출을 모두 보존하고 같은 라운드 중복을 거절한다.
10. 세 번째 라운드 마지막 제출만 자동 종료한다.
11. 여덟 명 사다리도 모든 경로와 제출 대상을 정확히 계산한다.

### 나머지 놀이

1. 이야기 주사위는 질문만 있는 미완성 묶음으로 끝나지 않는다.
2. 질문 주사위와 질문 릴레이는 참가자당 세 질문 전에는 끝나지 않는다.
3. 까바놀이는 마지막 참가자가 방장이 아니어도 마지막 답안과 종료를 저장한다.
4. 혼자와 인공지능 모드도 각 목표를 채우면 자동 결과 화면으로 이동한다.

### 점수와 실행 수명

1. 혼자와 인공지능 모드는 점수 요청을 보내지 않고 활동 결과만 보여 준다.
2. 학생 방장은 친구 방 결과에서 점수 요청과 점수 실패 화면을 만들지 않는다.
3. 교사 방장만 담당 학생 범위 안에서 실행 버전 `2` 점수를 요청할 수 있다.
4. 상태 버전, 점수 근거 버전, `playId`와 완료 종료 사유 가운데 하나라도 다르면 지급하지 않는다.
5. 같은 `playId` 지급 재요청은 기존 결과를 복원하고 점수를 중복 지급하지 않는다.
6. 같은 방 코드와 생성 시각에서 새 `playId`로 다시 끝낸 놀이는 이전 실행 키와 충돌하지 않는다.
7. `publish-award-result`는 교사 방장과 현재 실행만 허용하고 놀이 근거 필드를 바꾸지 못한다.
8. 미스터리 박스 추측, 이야기 주사위 대답과 이야기 문장은 질문 점수에 들어가지 않는다.
9. 질문 사다리의 서로 다른 세 라운드 질문은 보존되고 같은 라운드 중복은 거절된다.
10. `publish-award-result`에 결과 본문을 넣으면 거절되고 실제 실행별 점수 기록과 분석 스냅샷만 공유된다.
11. 질문-대답 짝 찾기의 획득 짝은 유효 질문 점수를 만들지 않고 완료된 경쟁 결과의 우승 판정에만 쓰인다.
12. 일찍 마침과 참가자 부족 종료에서는 점수 요청 자체를 보내지 않으며 어떤 점수도 적립되지 않는다.
13. 목표 시도를 채웠지만 모든 `activityScore`가 영인 경쟁 놀이는 참가와 완료 점수만 지급하고 우승자는 만들지 않는다.

### 화면 주제와 화면 크기

1. 밝은 화면과 어두운 화면에서 일곱 놀이의 시작, 진행, 대기와 결과 상태를 검사한다.
2. 질문 릴레이 최신 질문, 이야기 흐름, 최고 질문 결과와 사다리 선의 계산 대비를 중점 검사한다.
3. 모바일과 데스크톱에서 글자, 단추, 진행 표시와 사다리 그림이 겹치거나 잘리지 않는다.
4. 교사 미리보기와 학생 놀이에서 같은 화면 주제 결과가 나온다.
5. 일반 글자는 `4.5:1`, 큰 글자와 핵심 사다리 선은 `3:1` 이상의 계산 대비를 밝고 어두운 화면에서 만족한다.

## 구현 순서

1. 공통 규칙 모듈과 규칙 시험을 추가한다.
2. 방 시작 최소 인원과 옛 상태 호환 경계를 추가한다.
3. 공통 서버 명령 판정기와 비공개 방 응답 직렬화를 추가한다.
4. 짝 찾기 서버 카드 명령과 복원 흐름을 고친다.
5. 미스터리 박스 방 화면과 서버 명령을 추가한다.
6. 사다리 공통 경로, 세 라운드와 질문 확인 흐름을 추가한다.
7. 이야기 주사위, 질문 주사위, 질문 릴레이와 까바놀이의 자동 종료를 서버 판정으로 옮긴다.
8. 혼자와 인공지능 모드의 진행 목표와 자동 결과 화면을 맞춘다.
9. 공통 화면 주제 색과 사다리 그림 대비를 보완한다.
10. 실행 식별값, 점수 근거 버전, 결과 화면 수명과 놀이별 점수 상한을 새 라운드 규칙에 맞춘다.
11. 관련 시험, 전체 검사, 제품 빌드와 실제 브라우저 화면 검사를 실행한다.

## 데이터 영향

데이터베이스 스키마와 표를 바꾸지 않는다. 학생, 학급, 질문, 댓글, 알림, 기존 점수와 놀이 완료 자료를 일괄 읽거나 쓰지 않는다.

새 `stateVersion`, `playId`, `roundId`, 라운드와 공개 상태는 사용자가 새 놀이를 시작할 때 해당 임시 방의 기존 JSON 상태에 저장되는 값이다. 이는 별도 자료 이전이 아니다. 미스터리 박스의 비공개 물건도 임시 방 자료로만 존재하며 모든 클라이언트 응답에서 제거한다.

점수 정책 변경은 배포 뒤 새 규칙으로 완료한 활동에만 적용한다. 새 지급 로그는 기존 `roomCode` 문자열에 실행 식별값을 포함하며 표 구조는 바꾸지 않는다. 기존 총점과 기록을 다시 계산하지 않는다.

## 검증 기준

다음 검사가 모두 성공해야 한다.

```bash
npm run lint
npx tsc --noEmit
npm test
npm run build
```

추가로 다음을 확인한다.

- 데이터베이스 스키마와 자료 이전 파일에 차이가 없다.
- 실제 연결 데이터베이스에 시험 자료를 만들지 않았다.
- 두 명과 여덟 명 방의 시작, 차례, 자동 종료가 정상이다.
- 미스터리 박스 두 화면이 같은 질문과 차례를 보며 비밀 물건은 종료 전 노출되지 않는다.
- 짝 찾기 실패 뒤 다른 참가자가 정상적으로 카드를 뒤집는다.
- 사다리 경로와 배정 결과가 일치하고 세 모드 모두 질문을 작성하고 확인한다.
- 밝은 화면과 어두운 화면에서 핵심 글자와 그림이 읽힌다.
- 교사와 학생 목록의 인원과 시간이 실제 규칙과 같다.
- 학생 방과 혼자 및 인공지능 놀이에서 검증할 수 없는 점수 요청이 발생하지 않는다.
- 같은 방을 다시 시작한 두 실행의 결과와 허용된 점수 키가 서로 섞이지 않는다.
- 작업 트리에 이번 범위와 무관한 변경이 없다.

## 되돌리기와 완료 조건

설계 문서, 공통 규칙, 방 엔진과 놀이 화면 변경을 검토 가능한 작은 커밋으로 나눈다. 데이터베이스 구조와 기존 자료를 바꾸지 않으므로 자료 되돌리기 작업은 없다.

다음 조건을 모두 만족하면 구현을 완료한다.

1. 일곱 놀이의 참여 인원, 시간과 종료 목표가 공통 규칙과 일치한다.
2. 친구 방의 유효한 마지막 활동은 방장 여부와 관계없이 자동 종료된다.
3. 미스터리 박스와 짝 찾기의 두 기기 흐름이 멈추거나 갈라지지 않는다.
4. 질문 사다리의 경로, 질문 작성과 확인이 혼자, 인공지능과 친구 모드에서 동작한다.
5. 밝은 화면과 어두운 화면의 주요 대비 검사가 통과한다.
6. 기존 자료와 데이터베이스 스키마에 변경이 없다.
7. 전체 검사와 제품 빌드가 통과한다.
8. 구현 커밋을 원격 `main`에 푸시한다.
